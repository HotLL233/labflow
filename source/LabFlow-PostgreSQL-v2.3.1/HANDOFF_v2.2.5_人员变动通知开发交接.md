# LabFlow v2.2.5 开发交接总文档

> 本文是 LabFlow 历史开发上下文、已确认问题、解决方案、不可破坏的业务规则和 v2.2.5 实施手册。交给新的 Claude 实例后，应先完整阅读本文，再阅读同目录的 `开发方案_v2.2.5_人员变动通知字段与台账优化.md`。

## 0. Claude 开始工作前必须知道的事

1. 基线目录是 `C:\labflow\LabFlow-PostgreSQL-v2.2.4`，只读；目标开发目录是 `C:\labflow\LabFlow-PostgreSQL-v2.2.5`。
2. 不要在 v2.2.4 原目录改代码，不要覆盖旧版本安装包，不要把多个版本的源码混用。
3. 本次只处理人员变动通知的审计、完整字段、通知中心同步、新增项目表单、详情和软删除。方案外功能全部视为回归保护对象。
4. 人员反馈是通知/台账，不是主数据维护入口。不能直接写入用户表、项目表、实验室表或人员关联数据库。实际人员变动由管理员或分析检测组长审批后人工维护。
5. 不得恢复已经移除的部门角色、目标实验室、目标项目、新增项目名称等概念或入口。
6. 先执行基线检查和调用链阅读，再做最小局部修改。不要以大范围重构替代修复。
7. 数据库未连接时只能报告集成测试未执行，不能声称“全部测试通过”。
8. 完成后必须更新版本说明、测试报告、安装脚本输出名和校验文件，并报告实际修改文件、测试结果和安装包 SHA-256。

## 2. 历史开发时间线与已解决问题

- alpha.4-alpha.10 曾有公司级权限、部门角色、待确认归属、公共账号、统计和导出范围治理。后续 v2.2.0 已移除部门角色治理页面和接口，但业务记录 ownership 快照必须保留；不要重新引入这些治理链路。
- alpha.9 修复“未配置正式范围时默认放开全部部门”和连接池复用旧导出筛选的问题；人员通知读取范围时不能绕过正式数据范围。
- alpha.10 修复公共账号实际操作人权限、方法多类型导出重复和退回记录归属；不要在通知代码里复制一套独立权限判断。
- alpha.11 将“记住密码”和“保持登录”拆开，令牌由服务端管理；人员通知不得改变会话或登录状态。
- alpha.12-alpha.15 修复样品信息登记入口/新建权限分离、撤回取样、PDF 运行时、旧附件扩展名和预览缓存、补传删除附件、送样通知参数类型及退回记录组织快照。人员通知改动必须避开这些代码路径。

### 2.1 v1.2.0.15：人员反馈需求起点

最初需求是复用研发送样组长的编辑能力，按组长关联实验室选择实验室，再选择人员变动类型、人员、项目和方法。随后规则被多次澄清，最终以第 3 节权限和第 4 节业务规则为准，不以早期口头描述为准。

历史约束：人员反馈的所有操作不能改变程序内业务数据库；人员汇总表是独立的数据来源，用户表是唯一允许直接引用的主数据来源。

### 2.2 v1.3.x：人员变动通知与汇总表

v1.3.0 首次形成独立人员变动通知、近 7 天通知记录和“项目及人员汇总表.xlsx”导入/导出流程。管理员和分析检测组长查看/审批全部实验室，研发送样组长发起并查看自己的相关记录。通知先进入待审批，审批通过后才更新独立汇总表，并备份审批前文件；驳回不调整汇总表。

v1.3.1 固化了以下规则：管理员和分析检测组长可查看/导出全部实验室，研发送样组长只能查看/导出关联实验室；员工离职、实验室内调动、跨实验室调动默认勾选已有项目，取消勾选即取消关联，员工加入默认不勾选；管理入口增加人员反馈字段配置；检测方法逐条录入并禁止逗号、顿号、分号和换行，汇总表方法完整换行显示。

v1.3.2 修复了新增方法输入一个字符后失焦、旧数据库通知目标约束未升级和反馈字段自定义能力不足的问题。v1.3.3 修复了人员反馈提交后要等待后台 60 秒才发通知、规则编辑器显示英文以及反馈规则与审批特殊事件互斥失败的问题。

当时的设计是：人员反馈不写 PostgreSQL、旧人员反馈表、站内通知或审计表，只写独立 `personnel-change-data` 台账和 Excel 汇总表。v2.2.5 要新增审计镜像，是对这一设计的追溯补强，不是把业务台账迁入数据库。

汇总表核心维度为：实验室、实验室负责人、项目代号、该项目下的所有人员、检测方法。

重要结论：审批通过后可以更新独立汇总表，但不能自动更新用户、项目、实验室主数据。管理员或分析检测组长仍需手动完成真实人员调整。

### 2.3 v2.0.0：隐藏注册入口

登录页注册入口隐藏，但注册页面、路由和 API 为兼容旧流程仍保留。后续开发不得把“隐藏入口”误改成“删除注册功能”，除非有单独的新需求和迁移方案。

### 2.4 v2.1.0：通知字段与工作量筛选

- 工作量录入增加项目筛选，解决同一实验室多个项目使用同一检测方法时无法区分项目的问题。
- 通知中心新增人员通知反馈驳回规则。
- 通知字段目标是从录入表单和样品信息登记的自定义列自动同步，而不是在通知页面硬编码一套孤立字段。

历史坑：通知模板字段显示英文、不同通知混入无关字段、旧模板启用状态被覆盖。修复时必须保留旧模板已启用字段的显示状态、顺序、中文名和加粗属性；只把新增字段加入可配置候选。

### 2.5 v2.2.0-v2.2.3：教程、用户导入导出和阅读器

帮助与反馈经历了以下明确决策：

- 教程由管理员上传源文件，普通用户只能查看；教程内附件允许普通用户下载，上传权限仅管理员。
- 教程以列表/卡片展示，点击卡片后进入只读文档页；不能把教程入口替换成直接下载源文件。
- 预览采用连续上下滚动，参考国标网站的纵向阅读，不使用左右上一页/下一页翻页。
- 文档应尽量保留原格式、目录和附件链接；阅读窗口不能固定成过大导致无法查看完整页面，应有响应式宽度和目录定位。
- 已移除部门角色概念，相关页面、入口和链路不得恢复，且不能影响其他功能。

用户导入导出最终规则：导出表必须与导入模板格式一致，可直接重新导入；角色按导入模板的工作表/列表达。导出不得包含密码、启用状态或管理员状态。导入时旧角色映射问题不能重新出现。

### 2.6 v2.2.4：样品信息登记编辑修复

已修复并必须保护的行为：

- 编辑页部门显示实际中文名称，提交时仍使用部门 ID。
- 样品信息登记使用公共账号时，提交记录账号和实际送样人账号都具有相应编辑权限时，均可修改记录。
- 附件查看、上传、删除权限跟随上述实际送样人权限。
- 修复网络错误提示乱码和字符编码问题。
- 本版本没有改变样品登记之外的业务。

回归要求：人员变动通知和通知中心的改动不能触碰样品登记的编辑权限、附件逻辑、部门映射和错误提示代码。

## 4. 人员变动最终业务规则

### 4.1 变动类型

标准类型固定为：`员工加入`、`员工离职`、`实验室内人员调动`、`跨实验室人员调动`、`实验室新增项目`、`实验室新增方法`。历史输入中的“新员工加入”只做读取兼容，页面统一显示“员工加入”。不要重新引入“新增项目名称”等旧称入口。管理员可在系统配置中自定义新增、编辑、停用反馈字段，但不能删除仍被历史记录引用的字段定义。

### 4.2 实验室和项目选择

- 组长只能看到自己关联的实验室；管理员和分析检测组长可看到全部实验室。
- 实验室内人员调动的项目下拉必须显示该课题组长关联实验室的全部项目，不能只显示当前人员已关联项目。
- 已有人员在除“員工加入”外的变动类型中，应显示其已关联项目；涉及项目关联的变动默认勾选已关联项目，取消勾选表示取消该项目关联。
- 跨实验室人员调动不再显示目标实验室、目标项目字段。项目不选择时，语义是取消当前人员的全部项目关联。
- 所有项目、人员和实验室展示数据来自用户表和独立汇总表，不从人员反馈台账反向创建主数据。

### 4.3 实验室新增项目

- 新增项目代号必填且必须做重复检查。
- 项目人员输入框存在但可为空。
- 检测方法可为空；不能再强制“必须新增方法才可提交”。
- 如填写方法，禁止逗号、顿号、分号、换行等分隔字符；多个方法使用独立输入项/数组传递，不能依靠字符串拆分。
- 高新项目选择“是”时，高新项目名称必填。
- 审批通过后写入独立汇总表：项目代号必写；方法可以为空；项目人员可以为空。后续可通过“实验室新增方法”补充方法。

### 4.4 实验室新增方法

- 选择现有项目后填写新增方法名称。
- 输入框不能输入逗号、顿号、分号和换行。
- 修复曾出现的“输入一次就退出编辑状态”：受控输入组件不能因列表重渲染改变 key 或失去焦点，保存应显式触发，不能每次 onChange 立即提交。
- 汇总表方法单元格必须自动换行并显示完整方法名称，不截断为摘要。

### 4.5 通知性质和审批性质

- 创建、审批、驳回、删除均是通知台账动作。
- 审批通过只代表通知被确认，并更新独立汇总表；不得自动写用户、项目、实验室主数据。
- 真实人员变动由管理员或分析检测组长手动调整。
- 钉钉和程序内通知是发送结果，不是业务数据源；发送失败不能吞掉台账或审计错误。

## 5. 三类数据源边界

### 5.1 用户数据库

只引用用户、角色、组长与实验室关联等已有数据。禁止因人员反馈自动插入/更新/删除用户或角色。删除部门角色概念后，不得新增任何部门角色判断链路。

### 5.2 人员变动 JSONL 台账

- 默认目录：环境变量 `PERSONNEL_CHANGE_DATA_DIR`；未设置时为 `data/personnel-change-data`。
- 文件名：`notices-YYYY-MM.jsonl`。
- 保存通知提交、审批状态、驳回原因、发送状态和自定义字段。
- 它不是 PostgreSQL 业务表，也不应被改造成新数据库表。
- 删除采用追加式软删除，不能物理删除历史行；默认列表隐藏已删除记录。

### 5.3 项目及人员汇总表

- 文件：`项目及人员汇总表.xlsx`。
- 工作表：`当前实验室人员统计表`。
- 维度：实验室、实验室负责人、项目代号、项目下全部人员、检测方法。
- 支持导入和导出；导入导出格式应稳定，方法列可换行。
- 审批通过后的人员通知只按既有汇总表更新逻辑写入，不创建新的主数据表。

### 5.4 审计日志

审计是追溯镜像，不替代 JSONL 台账。创建、修改、审批通过、驳回、删除都要写审计，包含完整 before/after 快照。建议：`module='personnel_change'`、`table_name='personnel_change_notices'`、`business_no=notice_no`、`source='personnel_change'`。

## 6. v2.2.5 要实现的修复

### 6.1 统一完整 payload

在 `src/api/personnel_change_handler.rs` 提取一个公共 payload 构造函数，创建、审批、驳回全部复用。统一字段至少包括：

```text
notice_no, created_at, submitted_by, change_type, lab_name, lab_leader,
person_name, project, new_project_code, method, effective_at, is_high_tech,
high_tech_name, status, reviewed_by, reviewed_at, review_reason, notes,
delivery_status, updated_at, extra_fields.*
```

普通变动的 `project` 来自 `project_codes`；新增项目必须把 `new_project_code` 同时保留并用于消息展示。`method` 从方法数组去重后生成展示值，但原始数组不能丢失。`extra_fields` 原样保留。

### 6.2 通知中心字段

- 人员变动反馈和人员变动反馈驳回分别注册规则。
- 通知字段按事件适用范围过滤，研发送样相关通知不能混入无关字段。
- 表单字段和样品信息登记自定义列进入候选字段；已启用旧字段的名称、顺序、加粗和启用状态必须兼容。
- 默认只显示启用字段，隐藏字段通过新增/启用恢复；管理员明确隐藏的字段不能被升级逻辑自动打开。
- 编辑器必须显示中文字段名，同时保留字段键，不能把内部英文键直接展示给用户。
- 有模板时按模板顺序输出所有非空字段；无模板时完整兜底，不得只输出通知编号、实验室和项目三个摘要字段。
- 程序内通知和钉钉消息使用同一字段解析结果，避免两个渠道内容不一致。

### 6.3 详情、审计和删除

- 近 7 天记录默认保留现有排序和范围。
- 列表增加详情入口，详情显示所有标准字段、自定义字段、项目/方法、审批和发送状态。
- 创建、修改、通过、驳回、删除写审计；审计写入失败时对应台账操作必须失败，不得出现页面成功但审计缺失。
- 发起人只能删除自己的待审批/已驳回记录；管理员和分析检测组长可删除待审批/已驳回记录；已通过记录禁止删除。
- 删除需要原因，追加一条 `status='已删除'` 台账行并写审计，不回滚已通过的汇总表变更。
- 历史 JSONL 可进行幂等审计补录：不改原行、不重复补录、不重新发送钉钉，补录来源为 `personnel_change_backfill`。

## 7. 历史问题与常见坑清单

1. **字段不全**：台账保存了 `extra_fields`、高新项目和审批信息，但列表、兜底消息和程序内摘要只取少数键。解决方式是统一 payload 和字段渲染器，详情不能复用摘要。
2. **新增项目方法被误设为必填**：后端校验曾把项目代号和方法绑定。方法必须改为可选，项目代号仍必填。
3. **新增项目缺少项目人员**：汇总表更新逻辑其实支持 `person_name`，只是前端入口遗漏。补入口和类型，不重写汇总表核心逻辑。
4. **项目代号不显示**：新增项目使用 `new_project_code`，消息却主要读 `project_codes`。渲染时显式兼容两者。
5. **人员内调项目范围错误**：不能只按人员现有关联项目过滤，要按课题组长关联实验室的全部项目提供下拉。
6. **跨实验室字段死灰复燃**：目标实验室/目标项目已删除，兼容读取旧 JSONL 即可，不能恢复前端入口。
7. **通知未进审计**：JSONL 写入路径没有调用 `audit_repo`。新增审计镜像并处理失败回滚，不能只在前端显示已记录。
8. **通知无法查看完整内容**：列表摘要不是详情。新增详情弹窗/页面并显示标准字段和自定义字段。
9. **通知无法删除**：采用追加式软删除，不物理删除 JSONL，也不允许删除已通过记录。
10. **旧通知模板被升级覆盖**：字段合并必须以旧配置为优先；旧配置明确隐藏的字段不能自动启用。
11. **英文通知字段**：内部键仅用于程序，用户界面和消息标题必须使用中文映射。
12. **实时通知不触发**：检查规则事件名、规则启用状态、字段适用范围、队列入队和发送状态；不能仅修前端刷新。人员反馈和驳回使用稳定事件名 `personnel_change_feedback`、`personnel_change_feedback_rejected`。
13. **新增方法输入框失焦**：避免动态 key、数组索引重排和 onChange 保存；输入状态必须稳定直到用户提交。
14. **方法内容被截断**：汇总表和详情使用换行/自动高度，不用固定单行省略。
15. **乱码**：前端网络错误和后端 JSON 响应统一 UTF-8；不要通过替换字符掩盖编码链路问题。
16. **教程入口被替换成下载**：帮助与反馈必须保留列表卡片和只读阅读页，源文件下载是附件能力，不是教程入口。
17. **教程左右翻页**：阅读器使用纵向滚动、目录定位和响应式宽度；不要回退到上一页/下一页交互。
18. **教程显隐失效**：帮助文档/文章的 `is_visible` 历史上是 PostgreSQL `BIGINT`，按布尔值读取会导致按钮失效；读写时保持数值兼容，不要只改前端按钮。
19. **教程转换失败**：PDF/Office 转换失败时仍必须保留源文件下载，不要因预览失败删除上传记录；预览逻辑可参考样品附件分页处理。
20. **用户导出不能再导入**：导出必须严格复用导入模板工作表和列名；不能临时增加密码、启用状态、管理员状态列。
21. **角色治理概念复活**：v2.2.0 已移除公司级权限、数据治理审计、旧角色待映射和历史归属待确认页面/接口；不要恢复这些链路，业务记录自身 ownership 仍需保留。
22. **注册隐藏误删 API**：隐藏入口不等于删除路由和接口，除非新需求明确彻底禁用。
23. **安装包缺运行时**：安装脚本必须检查 PDF runtime、PostgreSQL runtime 和 VC++ 运行库；历史上缺 `vcredist_x64.exe` 会导致安装退出代码 2。热更新包不能替代完整服务器安装包。
24. **版本串线**：不要在带后缀的旧目录继续改，也不要把 `target`、`frontend/node_modules` 或生产数据复制成新版本事实来源。
