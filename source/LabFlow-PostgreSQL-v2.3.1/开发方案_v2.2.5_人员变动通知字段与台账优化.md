# v2.2.5 人员变动通知字段与台账优化方案

## 1. 文档目的

本方案用于修复 v2.2.4 中人员变动通知的以下问题：

- 通知记录未进入系统审计日志。
- 通知列表和详情不能查看完整提交内容。
- 通知中心的程序内消息、钉钉消息与人员变动台账字段不一致。
- “实验室新增项目”被错误要求必须填写检测方法。
- “实验室新增项目”缺少项目人员输入框。
- 已提交通知没有删除入口。

本方案只改人员变动通知、其通知模板、审计展示和新增项目表单，不修改样品信息登记、工作量录入、用户管理、帮助与反馈教程及其他无关功能。

## 2. 版本隔离

- 基线目录：`C:\labflow\LabFlow-PostgreSQL-v2.2.4`
- 新版本目录：`C:\labflow\LabFlow-PostgreSQL-v2.2.5`
- v2.2.4 原目录只读，不在原目录直接改代码。
- 版本号统一升级为 `2.2.5`、数值版本 `2.2.5.0`。
- 不复制生产数据库、配置文件、日志、用户密码或业务数据到新版本源码目录。

## 3. 当前实现与根因

### 3.1 三套数据流

1. 人员变动业务台账：
   - 文件：`src/api/personnel_change_handler.rs`
   - 目录：`PERSONNEL_CHANGE_DATA_DIR`，未设置时为 `data/personnel-change-data`
   - 文件：`notices-YYYY-MM.jsonl`
   - 用途：保存通知提交、审批状态和通知详情，不写入人员变动业务数据库表。

2. 通知中心队列和通知模板：
   - 队列入口：`src/service/notification_service.rs`
   - 队列和规则：`src/repo/notification_repo.rs`
   - 模板字段：`notification_templates.field_config_json`
   - 事件：`personnel_change_feedback`、`personnel_change_feedback_rejected`

3. 系统审计日志：
   - 审计写入：`src/repo/audit_repo.rs`
   - 审计接口：`src/api/audit_handler.rs`
   - 当前人员变动通知 JSONL 台账没有调用审计写入接口。

### 3.2 字段不全的具体原因

- `NoticeLog` 已保存 `extra_fields`、高新项目、审批和发送状态等字段，但 `PersonnelChangePage.tsx` 列表没有详情展示。
- 创建通知 payload 没有完整补入实验室负责人、更新时间、发送状态等字段。
- 新增项目时项目代号存于 `new_project_code`，而通知正文主要读取 `project_codes`，导致项目代号可能不显示。
- `notification_text()` 的人员变动兜底正文只输出通知编号、变动类型、实验室、人员和驳回原因。
- 程序内通知使用 `in_app_body` 摘要，不等于钉钉模板正文。
- 人员反馈自定义字段只有 `enabled=true` 且 `notify=true` 时才进入候选字段；旧模板中没有的字段默认在隐藏候选区，不会自动显示。
- 现有模板字段配置兼容旧字段，但没有统一的人员变动字段注册表。

### 3.3 新增项目问题原因

- 后端 `validate_notice()` 当前要求“实验室新增项目”同时填写项目代号和至少一个检测方法。
- 前端只在人员变动类型为员工加入、离职、实验室内调动、跨实验室调动时显示人员框。
- `apply_summary_change()` 已经支持使用 `person_name` 写入新项目人员，因此缺少的是表单入口和校验规则，而不是汇总表更新能力。

## 4. 统一字段字典

人员变动通知、程序内通知、钉钉通知、详情页和审计快照统一使用以下字段键：

| 字段键 | 中文名称 | 适用说明 |
|---|---|---|
| `notice_no` | 通知编号 | 所有通知 |
| `created_at` | 提交时间 | 所有通知 |
| `submitted_by` | 提交人 | 所有通知 |
| `change_type` | 变动类型 | 所有通知 |
| `lab_name` | 实验室 | 所有通知 |
| `lab_leader` | 实验室负责人 | 从项目及人员汇总表读取 |
| `person_name` | 人员/项目人员 | 普通变动人员；新增项目时为项目人员 |
| `project` | 关联项目 | 普通变动的项目多选结果 |
| `new_project_code` | 新增项目代号 | 仅新增项目 |
| `method` | 检测方法 | 新增方法或新增项目可选方法 |
| `effective_at` | 生效日期 | 所有通知 |
| `is_high_tech` | 高新项目 | 新增项目 |
| `high_tech_name` | 高新项目名称 | 高新项目为“是”时必填 |
| `status` | 变动状态 | 待审批、已通过、已驳回、已删除 |
| `reviewed_by` | 审批人 | 审批后填写 |
| `reviewed_at` | 审批时间 | 审批后填写 |
| `review_reason` | 驳回/审批说明 | 驳回或审批说明 |
| `notes` | 备注 | 所有通知 |
| `delivery_status` | 通知发送状态 | 程序内和钉钉发送结果 |
| `updated_at` | 更新时间 | 台账最后更新时间 |
| `extra_fields.*` | 自定义字段 | 管理员配置且允许通知的字段 |

兼容字段：`target_lab_name`、`target_project_codes`、`new_project_name` 保留读取能力，不新增表单入口，不恢复已移除的业务概念。

## 5. 详细改造方案

### 5.1 完整 payload

在 `personnel_change_handler.rs` 增加单一的 payload 构造函数，创建、审批、驳回均复用，不在三个位置分别拼 JSON。

payload 要求：

- `project`：普通变动取 `project_codes`；新增项目取 `new_project_code`。
- `new_project_code` 单独保留。
- `method`：取 `method_names` 去重后用“、”连接。
- `lab_leader`：按实验室从当前汇总表读取负责人。
- `person_name`：普通变动为人员；新增项目为项目人员，可为空。
- `extra_fields` 原样保留，字段值不得丢失。
- 追加 `delivery_status`、`review_status`、`reviewed_by`、`reviewed_at`、`review_reason`、`updated_at`。
- 驳回 payload 必须基于审批后的完整通知对象生成。

### 5.2 通知模板字段

修改 `src/repo/notification_repo.rs`、`src/service/notification_service.rs` 和前端模板编辑器：

- 人员变动反馈与人员通知反馈驳回分别加载完整字段。
- 自定义字段按 `fields.json` 的 `enabled`、`notify` 和适用变动类型过滤。
- 旧模板中明确配置的字段保留原显示状态、名称、顺序和加粗属性。
- 新增标准字段进入“可新增字段”列表。
- 旧配置没有明确记录的新标准字段按默认启用，避免升级后通知内容突然变少。
- 管理员明确隐藏的字段不能被自动重新启用。
- 模板编辑器展示中文名称和字段键，支持启用、隐藏、排序、改名和加粗。

### 5.3 钉钉和程序内消息

调整 `notification_text()` 与 `notification_text_with_template()`：

- 有模板时，钉钉正文按模板字段顺序输出所有非空字段。
- 无模板或模板读取失败时，兜底正文也输出完整标准字段。
- 新增项目无方法时仍必须显示新增项目代号。
- 驳回消息必须显示通知编号、变动类型、实验室、人员、项目、审批人、审批时间和驳回原因。
- 程序内消息不再仅使用“标题 + 实验室 + 项目”摘要，改为完整字段摘要或可展开详情。
- 空字段不输出，避免产生空白行。

### 5.4 通知详情页面

修改 `frontend/src/pages/PersonnelChangePage.tsx`：

- 近 7 天列表保留现有默认范围和排序。
- 增加“查看详情”按钮。
- 详情弹窗显示所有标准字段、自定义字段、项目列表、方法列表、发送状态和审批信息。
- 列表中的“项目/方法”只做摘要，不能代替详情。
- 已删除记录默认不显示；管理员可在需要时查看删除状态和删除原因。

### 5.5 审计日志

人员变动通知继续以 JSONL 保存业务台账，但新增审计镜像：

- 创建：`create`
- 修改：`update`
- 审批通过：`approve`
- 驳回：`reject`
- 删除：`delete`

建议使用 `module='personnel_change'`、`table_name='personnel_change_notices'`，`business_no=notice_no`，`source='personnel_change'`。

审计记录必须包括：

- 操作账号、操作时间、通知编号。
- 完整 before/after JSON 快照。
- 标准字段和自定义字段。
- 审批人、审批时间、驳回原因。
- 删除原因。

审计列表增加“人员变动通知”模块筛选及中文名称；详情页支持查看 JSON 字段差异。审计写入失败时，创建或审批操作应失败并回滚对应台账状态，不能产生“页面提示成功但审计缺失”。

### 5.6 新增项目表单

仅修改人员变动通知表单和后端校验：

- 新增项目代号：必填。
- 项目人员：可选，复用 `person_name` 字段。
- 检测方法：可选。
- 高新项目：可选；选择“是”时高新项目名称必填。
- 项目代号重复仍禁止提交。
- 方法如填写，继续禁止逗号、顿号、分号和换行。

审批通过后的汇总表行为：

- 有方法则写入方法。
- 无方法则方法列为空，后续可通过“实验室新增方法”补充。
- 有项目人员则写入“实验人员”列。
- 无项目人员则实验人员为空。

### 5.7 删除已提交通知

建议使用追加式软删除，不修改或物理删除历史 JSONL 行：

- 发起人可删除自己“待审批”或“已驳回”的通知。
- 系统管理员、分析检测组长可删除“待审批”或“已驳回”的通知。
- 已通过通知禁止直接删除，避免汇总表与通知台账不一致。
- 删除必须填写原因。
- 写入一条最新状态为“已删除”的台账记录，同时写入审计日志。
- 默认近 7 天列表隐藏已删除记录。
- 删除不回滚已经通过审批产生的汇总表变更。

如确需纠正已通过通知，另发新的人员变动通知或走管理员人工更正流程，本版本不新增自动回滚。

### 5.8 历史数据兼容

增加一次幂等的历史审计补录：

- 扫描已有 `notices-*.jsonl`。
- 已有同一 `module/table_name/business_no/action` 的审计记录不重复写入。
- 历史通知不重新发送钉钉消息。
- 缺少的新字段显示为空。
- 不修改原 JSONL 内容。
- 补录记录的 `source='personnel_change_backfill'`。

## 7. 测试验收

### 功能测试

- 新增项目只填写项目代号即可提交。
- 新增项目可填写一个或多个项目人员。
- 新增项目有方法、无方法均可审批。
- 新增项目通知显示项目代号。
- 员工加入、离职、实验室内调动、跨实验室调动、实验室新增方法行为不变。
- 通知详情显示全部标准字段和自定义字段。
- 程序内通知和钉钉通知字段一致。
- 模板隐藏字段不显示，新增字段可恢复显示。
- 旧模板已启用字段状态保持不变。
- 创建、审批通过、驳回、删除均写入审计日志。
- 历史通知补录不重复、不触发外部发送。
- 已通过通知不可删除；删除原因可在审计查看。
