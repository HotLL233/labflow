# 检测类型管理与实验室显示范围优化方案

> 方案基线：`v2.2.14`（`C:\labflow\LabFlow-PostgreSQL-v2.2.14-all-export-formulas-source`）  
> 目标版本：建议 `v2.2.16`，版本号以发布时确认为准  
> 明确废弃：`v2.2.15-auxiliary-work-source` 不作为代码或数据库基线

## 1. 目标

在保留 2.2.14 全部现有功能和数据的前提下：

1. 将检测类型作为独立主数据进行管理。
2. 默认所有启用实验室、所有入口均显示所有启用检测类型。
3. 管理员可以按“检测类型 + 实验室 + 入口”关闭显示范围。
4. 新增实验室或新增检测类型时自动继承“显示”，不需要补数据。
5. 工作量、研发送样、样品信息登记三个入口使用同一套后端过滤规则。

## 2. 当前问题与根因

- `method_types` 只有名称、排序、软删除字段，没有实验室范围配置。
- 实验室、项目、方法已有 `show_in_work`、`show_in_rd`、`show_in_sample_info`，但这些只能控制对象是否进入入口，不能控制某个检测类型在某实验室是否可见。
- 前端部分页面直接加载全量检测类型，容易出现入口之间显示不一致。
- 类型名称被方法关联、记录、统计和导出引用，直接删除或改造关联关系会影响历史数据。

因此本次只增加“检测类型可见性”这一层，不改现有方法与类型的关联模型，不把 2.2.15 的辅助工作代码带入本版本。

## 3. 业务规则

### 3.1 入口

沿用系统已有入口标识：

| 标识 | 页面含义 |
|---|---|
| `work` | 分析检测/工作量录入 |
| `rd` | 研发送样 |
| `sample_info` | 样品信息登记 |

检测类型最终可见条件为：

```text
用户有该实验室权限
AND 实验室在该入口开启
AND 项目在该入口开启
AND 方法在该入口开启
AND 检测类型在该实验室/入口可见
```

### 3.2 默认值与覆盖

- 没有可见性覆盖记录时，视为可见（默认全开）。
- 管理员取消某实验室的勾选时，只保存一条“关闭”覆盖记录。
- 重新勾选时删除关闭记录或改为开启，最终效果相同。
- 新增实验室、新增检测类型不需要批量生成映射，查询时自动可见。
- 停用检测类型沿用现有软删除规则：禁止新录入，历史记录、统计和导出仍保留类型名称。
- 检测类型可以在某个入口全部关闭，但界面需提示该入口将没有可选类型；不删除历史数据。
- 本版本继续保持“一个方法只能关联一个检测类型”的 2.2.14 约束，不扩展多类型方法。

### 3.3 权限

- 复用现有 `manage:methods` 权限，管理员及已有检测类型管理人员可配置。
- 普通用户只能看到自己有权限实验室中的可见类型。
- 不新增注册、部门角色或旧角色映射逻辑。

## 4. 数据库设计

新增表（名称可按项目命名规范调整）：

```sql
CREATE TABLE method_type_visibility (
    id BIGSERIAL PRIMARY KEY,
    method_type_id BIGINT NOT NULL REFERENCES method_types(id),
    group_id BIGINT NOT NULL REFERENCES project_groups(id),
    portal VARCHAR(32) NOT NULL,
    is_visible BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (method_type_id, group_id, portal),
    CHECK (portal IN ('work', 'rd', 'sample_info'))
);
CREATE INDEX idx_method_type_visibility_group_portal
    ON method_type_visibility(group_id, portal, method_type_id);
```

实现约定：只写入管理员主动关闭的记录，因此不存在记录即为可见。查询必须同时排除已软删除的检测类型和实验室。若实现选择保存全量映射，也必须保留“新增实验室/类型默认全开”的事务逻辑，不能依赖人工补录。

迁移要求：

- 使用独立、可重复执行的迁移标识，例如 `detection-type-visibility-v1`。
- 只 `CREATE TABLE/INDEX`，不修改或回填 `method_types`、`method_type_links`、项目、方法及历史记录。
- 启动迁移失败时服务明确报错并停止使用新功能，不得静默回退为全量数据泄漏。
- 回滚只删除本表及索引，不触碰既有业务表。

## 5. 后端实现

### 5.1 统一可见性查询

在 repository/service 层增加一个共享条件或查询函数，输入 `method_type_id`、`group_id`、`portal`，按“无关闭记录即可见”判断。所有入口禁止各自拼接不同规则。

需要接入的路径：

- `GET /api/method-types`：保留无参数时的现有全量管理列表；增加可选 `portal`、`group_id`，录入页面传参后返回可见类型。
- `GET /api/methods`：已有 `portal`、`group_id` 参数，增加类型可见性条件。
- 项目及方法关联查询：按入口和实验室复用同一条件，防止项目选择后又出现不可见类型的方法。
- 工作量录入、研发送样、样品信息登记页面均只能使用上述过滤后的结果。

### 5.2 管理接口

建议新增：

- `GET /api/method-types/:id/visibility?portal=...`：返回实验室列表及每个实验室的有效勾选状态。
- `PUT /api/method-types/:id/visibility`：提交某个入口的实验室勾选结果，后端校验入口、类型和实验室均有效，并在一个事务内保存。

保存接口必须：

- 去重实验室 ID，拒绝不存在、已删除或无权配置的实验室。
- 记录审计日志（类型、入口、关闭/恢复的实验室名称和操作人）。
- 返回保存后的有效状态，前端以返回值刷新，避免“页面勾选成功但实际未保存”。

### 5.3 历史数据保护

可见性只影响新录入时的选项和当前入口展示，不对历史记录做删除、改类型或重算。统计、详情、通知和导出继续按记录保存的类型读取；已停用类型显示为历史名称或“已停用”标记。

## 6. 前端设计

管理入口：`管理 → 检测类型管理`，保留现有名称、排序、启用/删除能力，新增：

- 分析检测显示实验室数
- 研发送样显示实验室数
- 样品信息登记显示实验室数
- “配置显示范围”按钮

配置弹窗：

1. 入口使用 Tab 或分区切换，分别显示三个入口。
2. 实验室列表显示实验室名称，不显示数据库 ID。
3. 默认全部勾选；提供全选、清空、反选和按名称搜索。
4. 关闭弹窗或切换入口前提示未保存修改。
5. 保存中禁用重复提交，成功后显示“已保存 X 个实验室可见”。
6. 当入口关闭全部类型时显示明确警告，但不阻止管理员保存。

录入页面在选择实验室后再加载检测类型和方法，实验室切换时清空不再可见的已选值并要求重新选择，避免提交隐藏类型。

## 7. 版本隔离与实施步骤

1. 只读复制 2.2.14 目录，创建独立工作目录，例如 `LabFlow-PostgreSQL-v2.2.16-detection-type-visibility-source`。
2. 复制后先核验 `VERSION=2.2.14`、数据库连接配置、静态资源和安装脚本；禁止从 2.2.15 复制文件。
3. 第一阶段：数据库迁移、共享查询和管理接口。
4. 第二阶段：管理页面和三个录入入口接入过滤。
5. 第三阶段：权限、审计、导入导出及回收站回归检查。
6. 第四阶段：构建独立测试包，使用独立端口和独立数据库进行场景测试。
7. 验收通过后再更新版本号、更新说明和安装包；2.2.14 原目录保持不变。

本次明确不修改：金额/工作量计算、导出公式、人员反馈、辅助工作、通知模板、附件预览、用户权限模型及任何与检测类型显示无关的代码。

## 8. 实际使用场景验收

不做接口级测试，以登录后的实际页面操作为准：

| 场景 | 预期结果 |
|---|---|
| 新安装后进入三个入口 | 所有有权限实验室默认显示全部启用检测类型 |
| 管理员关闭“液相”在实验室 A 的分析检测显示 | A 的分析检测不再出现；其他实验室仍出现；研发送样和样品登记不受影响 |
| 关闭同类型在研发送样显示 | 仅研发送样入口隐藏，另外两个入口保持原状态 |
| 切换实验室后重新选择项目/方法 | 类型和方法列表只显示当前实验室/入口允许项 |
| 新增实验室 | 已有类型自动显示，无需配置补录 |
| 新增检测类型 | 所有现有实验室、三个入口默认显示 |
| 停用检测类型后提交新记录 | 不能新选；历史记录详情、统计、通知和导出仍有原类型 |
| 普通用户登录 | 只能看到权限范围内实验室及其可见类型 |
| 管理员编辑并刷新页面 | 配置持久化，刷新和重新登录后状态一致 |
| 2.2.14 原有工作量、金额、导出、附件、通知、人员反馈流程 | 功能和结果与基线一致 |

## 9. 风险与回滚

- 风险：某些旧调用未传 `group_id`。处理：管理列表允许无参数全量返回；录入入口强制传实验室 ID，并在后端拒绝缺少必要范围的提交。
- 风险：配置错误导致入口无类型。处理：保存前提示影响范围，保留“清空”操作但要求二次确认。
- 风险：迁移或查询异常。处理：版本启动健康检查验证新表和查询；失败则停止新版本启动，2.2.14 服务和数据库不回滚、不改写。
- 回滚方式：停止新版本服务，切回 2.2.14；新表无历史表依赖，保留或删除均不影响 2.2.14 数据。

## 10. 完成标准

- 三个入口的检测类型、方法和项目选择均按同一规则过滤。
- 默认全开、新增自动继承、按实验室和入口关闭均验证通过。
- 历史记录、统计、通知、导出未被隐藏或修改。
- 2.2.14 基线目录无改动，2.2.15 未被引用。
- 场景验收表全部通过后，才允许构建正式安装包。
