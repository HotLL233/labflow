# LabFlow v1.2.0-alpha.15 修复方案

依据：`docs/测试报告_v1.2.0-alpha.15_实际场景.md`。本方案只针对实际用户场景验收，不把接口测试作为验收替代；交接文档仅作为版本和业务规则依据。

## 1. 结论与发布门槛

当前版本不能作为“全部功能通过”版本发布。以下四项必须修复并完成真实页面回归后，才允许进入候选发布：

| 编号 | 问题 | 优先级 | 影响 |
|---|---|---:|---|
| P1-01 | 新建实验室的所属部门未持久化 | P1 | 研发送样提交被阻断，执行部门无法形成快照 |
| P1-02 | 用户新建失败仍提示成功 | P1 | 管理员误以为账号可用，后续登录和业务授权失效 |
| P1-03 | 样品信息登记部门下拉为空 | P1 | 样品登记、附件补传、退回待修改闭环全部无法进入 |
| P1-04 | PostgreSQL 连接数耗尽 | P1 | 页面出现“连接数过多”，分析记录查看等功能中断 |

注册路由缺失属于 P2；附件旧文件预览、补传删除、退回、通知外发、备份恢复等场景本轮未完成，不能标记为通过，必须在 P1 修复后补做现场验收。

## 2. P1 修复项

### P1-01 实验室所属部门保存失败

**根因判断**

- `ManagePage.tsx` 新建实验室时的初始对象没有设置 `division_id`，选择框虽然存在，但首次打开时状态对象不含该字段。
- `handleSaveGroup` 已将 `division_id` 发送给 `createGroup`；后端 `group_repo::create` 也有对应 INSERT 字段，因此优先修复前端状态初始化，不先改数据库结构。
- 同时检查更新时“显式置空”和“指定部门”两种语义，避免修复后无法取消归属。

**修改范围**

- `frontend/src/pages/ManagePage.tsx`
- `frontend/src/api/masterData.ts`（仅在类型定义需要明确时修改）
- `src/models/group.rs`、`src/repo/group_repo.rs`（补充更新语义测试或必要的小修复）

**最小修复步骤**

1. 新建实验室初始状态明确加入 `division_id: null`。
2. 保存前校验实验室名称；保存后以接口返回对象刷新列表，不仅依赖本地状态。
3. 编辑已有实验室时分别验证：选择部门写入对应 ID；选择“未分配”能写回 NULL。
4. 若后端更新 DTO 使用 `Option<Option<i64>>`，确认前端发送 `null` 时能被解析为“显式置空”，并保留“字段缺省=不更新”的语义。

**场景验收**

管理员登录 → 新建部门 → 新建实验室并选择该部门 → 保存 → 刷新管理页，所属部门仍显示；进入研发送样 → 选择该实验室 → 选择项目、方法、送样人 → 提交一条记录成功；取样后记录显示执行部门。再次编辑为“未分配”并保存，刷新后显示未分配，研发送样应按业务规则阻止提交并给出明确提示。

### P1-02 用户创建成功提示与数据库不一致

**根因判断**

- `ManagePage.tsx` 的新建分支直接 `await createUser(...)` 后显示“用户创建成功”，没有检查返回体 `result.code`。
- 后端 `user_handler::create_user` 和 `user_repo::create` 使用事务并在提交后返回统一响应；因此业务校验失败时，前端会把失败响应误报成成功，不能先认定为数据库事务丢数据。
- 需要保留一次失败响应的实际 `code/message`，确认是角色、实验室/部门归属校验还是其他业务条件触发。

**修改范围**

- `frontend/src/pages/ManagePage.tsx`
- `frontend/src/api/admin.ts`、`frontend/src/api/http.ts`（复用现有 `requireApiSuccess` 或同等统一处理）
- `src/api/user_handler.rs`、`src/repo/user_repo.rs`（仅补充错误日志、事务回归测试或发现确有后端问题时修正）

**最小修复步骤**

1. 新建用户保存分支读取 `createUser` 返回值；`code !== 0` 时显示后端消息、保留弹窗内容、不关闭弹窗、不刷新为成功。
2. `code === 0` 后再关闭弹窗、刷新用户列表，并用用户名或 ID 验证列表中出现该用户。
3. 对角色要求实验室、公共账号必须绑定部门等校验，前端在提交前做必要提示，后端校验继续作为最终约束。
4. 后端在事务失败路径记录可检索的操作日志，但不得记录明文密码。

**场景验收**

管理员 → 用户管理 → 新建普通送样员，绑定部门、实验室、角色 → 保存；页面提示成功，刷新后用户仍在列表，退出管理员后该用户能登录且只能看到授权门户。故意不绑定必填实验室或重复用户名，页面必须显示失败原因，不能显示“创建成功”，数据库不得产生半条用户或孤立角色关联。

### P1-03 样品信息登记部门下拉为空

**根因判断**

- `SampleInfoEntry.tsx` 通过 `Promise.all` 同时加载部门、实验室、项目；整个链路的 `.catch(() => {})` 静默吞掉异常，任何一个请求失败都会表现为空下拉，用户无法区分“无数据”和“加载失败”。
- 后端 `division_repo::list_for_portal` 的 `portal=sample_info` 过滤逻辑本身符合 `is_active`、`show_in_sample_info` 规则；需用页面登录态确认返回数据、权限范围和数据库字段值是否一致。

**修改范围**

- `frontend/src/pages/SampleInfoEntry.tsx`
- `frontend/src/api/masterData.ts`
- `src/api/division_handler.rs`、`src/repo/division_repo.rs`
- 必要时检查 `authz_service` 对样品信息门户的数据范围过滤

**最小修复步骤**

1. 将三组初始化请求拆分为可分别处理的加载状态；至少保留部门请求错误信息并在页面显示可操作提示。
2. 成功返回空数组时显示“当前账号无可用部门/请联系管理员”，不要与请求失败共用空白状态。
3. 在管理员配置中确认部门 `is_active=1`、`show_in_sample_info=1`，关联实验室同样启用样品门户显示。
4. 核对前端查询参数为 `portal=sample_info`，后端响应字段与 `Division` 类型一致；若权限过滤导致空列表，返回明确的权限提示。
5. 修复后先恢复部门 → 实验室 → 项目 → 样品登记的完整链路，再验证附件功能。

**场景验收**

普通送样员登录 → 样品信息登记 → 部门下拉出现已启用部门 → 选择部门后实验室和项目候选正确联动 → 填写登记表并提交 → 刷新记录仍存在。随后上传附件、补传、删除附件、编辑并再次保存，页面和记录状态一致。

### P1-04 PostgreSQL 连接耗尽

**根因判断**

- `src/db/connection.rs` 生产池 `max_size=40`，而本轮测试 PostgreSQL `max_connections=20`；应用池上限高于数据库总连接预算，叠加页面并发初始化请求和后台维护/通知任务，达到连接上限是可预期风险。
- 还需确认每个查询是否及时释放连接，后台循环是否串行执行，以及页面是否重复挂载导致重复请求。不能只提高数据库 `max_connections` 作为修复。

**修改范围**

- `src/db/connection.rs`
- `src/main.rs`
- 需要时检查各 API handler 的连接持有范围和前端页面初始化 `useEffect`
- 部署配置中的数据库连接预算

**最小修复步骤**

1. 将连接池上限改为可配置，并默认不超过数据库可用连接预算；为应用、迁移、后台任务预留余量，具体数值以部署规格压测后确定，禁止固定使用 40 覆盖所有环境。
2. 降低 `min_idle`，避免低负载时预占过多连接；连接超时错误要在页面显示“系统繁忙，请稍后重试”，并写入结构化日志。
3. 检查后台备份、通知重试、日志维护任务，确保同一轮只启动一个任务实例，且每次任务结束后释放连接。
4. 检查前端页面重复初始化和并发请求，避免同一页面重复拉取相同主数据；不要用无限重试掩盖连接耗尽。
5. 在测试环境以数据库 `max_connections=20` 连续执行真实页面路径，观察连接数峰值、错误率和恢复时间。

**场景验收**

冷启动 → 管理员登录 → 连续打开管理、研发送样、分析检测、统计、通知页面并执行一次录入/查询 → 反复刷新 10 次；全程无“连接数过多”，记录、统计和通知页面均能稳定加载。停止后台任务后连接应在合理时间回落，服务重启后可恢复。

## 3. P2 与发布前补验项目

### P2-01 注册页面路由

`frontend/src/pages/RegisterPage.tsx` 存在，但 `frontend/src/App.tsx` 未注册 `/register`。明确产品策略后选择其一：

- 若允许自助注册：注册路由、入口、验证码/审批和默认角色一起补齐，并按实际注册→登录场景验收。
- 若不允许自助注册：删除或隐藏死代码页面，并在帮助文档中说明账号由管理员创建。

### P2-02 附件与状态闭环

P1-03 修复后必须按真实页面完成：样品登记提交、附件上传、补传、删除、旧无扩展名 PDF/Word 预览、预览失败自动重试、退回待修改、已取样/退回权限限制。Rust 单元/集成测试通过不能替代页面验收。

### P2-03 通知、导出、治理和运维

使用隔离环境补验通知渠道配置与发送、统计筛选与 Excel 下载、主数据/业务数据导入导出、审计日志、回收站恢复/永久清理、备份下载与恢复、日志维护和安装/热更新包。涉及外部 Webhook 或破坏性操作时，使用专用测试账号、测试目录和可恢复备份，禁止连接生产系统。

## 4. 数据兼容与迁移注意事项

1. 本四项修复原则上不新增表结构，不需要数据迁移脚本。
2. 发布前在备份副本上检查：`project_groups.division_id`、用户主部门/业务部门关联、`user_roles`、`user_groups`、部门与门户显示字段。
3. 对历史实验室记录只做核查，不批量猜测补部门；若业务确认映射关系，另行提供可审计的一次性修复脚本。
4. 连接池参数属于部署配置，按环境单独调整，不写入历史业务数据迁移。
5. 修复版本必须保留数据库备份、迁移日志和应用版本号，便于回滚定位。

## 5. 回归测试顺序（全部按页面实际操作）

1. 启动隔离数据库和服务，确认连接池、日志和备份目录配置。
2. 管理员登录，创建部门、实验室并验证刷新后所属部门持久化。
3. 创建业务用户，验证成功/失败两条路径及普通用户登录权限。
4. 研发送样：项目、方法、送样人选择，提交、查询、取样、撤回/退回。
5. 样品信息登记：部门→实验室→项目联动，提交、编辑、附件上传/补传/删除、退回。
6. 分析检测：门户进入、工作量录入、记录查看、统计筛选和导出。
7. 通知、审计、回收站、备份恢复和权限边界场景。
8. 连续刷新和多页面操作，确认连接数稳定；最后执行构建、`cargo check`、`cargo test --lib`，并记录结果。

## 6. 风险与回滚

**风险**：修复部门状态后，旧数据中未配置部门的实验室仍会被业务规则拦截；用户创建校验收紧后，历史上依赖隐式角色/实验室的脚本可能失败；连接池下调过度会增加等待时间；样品门户权限过滤可能暴露原有配置问题。

**回滚**：先停止新版本服务，保留数据库和附件备份；恢复上一版应用包及连接池配置；不回滚已提交的合法业务数据。若发现错误数据写入，只能依据审计日志和备份执行经批准的数据修复，禁止直接删除生产记录。

## 7. 完成判定

只有在四个 P1 场景全部通过、附件/退回闭环完成、连接数稳定，且报告中所有“未执行/阻断”项被明确标记为通过或经产品负责人书面豁免后，才能将 v1.2.0-alpha.15 判定为可发布候选版本。
