# 公司级组织、权限与数据治理实施方案

**文档版本：** v1.0  
**适用系统：** 样品管理系统  
**编制日期：** 2026-08-12  
**适用范围：** 研究院、动保一部、动保二部、质量部及后续新增部门

---

## 1. 建设目标

当系统扩展为全公司使用时，需要同时满足以下目标：

1. 各部门仅查看和操作自身被授权的业务数据。
2. 跨部门送样、检测和协作可正常执行，且每条数据的发起、执行和项目归属明确。
3. 总部或多部门管理人员可进行跨部门汇总，也可按部门分别统计。
4. 公共账号仅作为代操作入口，不能成为实际送样人、检测人或取样人的业务归属。
5. 角色、权限、部门范围和实验室关系可由管理员清楚配置、核查和追溯。

## 2. 总体原则

系统权限由三层共同决定：

1. **功能权限：** 用户是否可以执行某项功能，例如取样、退回、导出。
2. **数据范围：** 用户可以处理哪些部门的业务数据。
3. **记录关系：** 对某一条具体记录是否满足创建人、实际业务人员、组长或管理员等业务规则。

一次操作必须同时满足以上三层。前端只负责显示或隐藏入口，后端必须重复校验，不能依赖前端保护数据。

### 2.1 权限判定流程

```text
登录账号
  -> 是否拥有功能权限？
  -> 该记录所属部门是否位于角色数据范围内？
  -> 是否满足本人 / 实际业务人员 / 组长 / 管理员等记录规则？
  -> 允许操作
```

### 2.2 全局固定规则

1. 未配置数据范围，等于无业务数据权限，不等于全部部门。
2. 全公司数据范围只能由系统管理员明确配置。
3. 用户拥有多个角色时，功能权限取并集，数据范围取并集。
4. 权限校验使用部门 ID、实验室 ID、项目 ID 等稳定标识，不使用名称作为判断条件。
5. 历史记录的部门归属必须保留快照，后续组织调整不能改变既往统计结果。

## 3. 组织对象定义

| 对象 | 正确定义 | 不承担的职责 |
|---|---|---|
| 部门 | 公司组织和数据隔离的最小单位 | 不等于实验室，不等于分析组 |
| 实验室 | 实际执行检测的业务单元，唯一归属一个执行部门 | 不作为人员组织归属 |
| 分析组 | 某部门内拥有分析检测员或分析检测组长角色的启用人员集合 | 初期不单独归属实验室 |
| 项目 | 业务项目，必须明确一个项目归属部门 | 不代替人员权限范围 |
| 用户 | 具有主归属部门、可承担业务部门和部门角色 | 不因登录公共账号改变归属 |
| 角色模板 | 定义一类角色可做哪些功能 | 不直接授予用户 |
| 部门角色 | 模板在某个部门下的具体角色，包含数据范围 | 不可无边界跨部门复用 |
| 公共账号 | 为代操作而设置的登录入口 | 不作为实际业务人员 |

### 3.1 分析组的定义和使用

“研究院分析组”不是实验室，也不需要作为实验室子级维护。其定义为：

```text
主归属部门或可承担业务部门为“研究院”
且账号启用
且拥有“分析检测员”或“分析检测组长”部门角色
```

分析公共账号选择人员时，系统按此规则展示人员卡片。

## 4. 角色模板、部门角色和数据范围

### 4.1 改动前后

| 项目 | 改动前 | 改动后 |
|---|---|---|
| 角色 | 直接创建、直接勾选权限、直接赋予用户 | 先定义角色模板，再创建部门角色 |
| 部门范围 | 可能分散在权限、实验室、公共账号等位置 | 每个部门角色有独立业务数据范围 |
| 用户权限 | 角色含义与部门范围混在一起 | 用户分配部门角色，角色控制功能和范围 |
| 空范围 | 容易被理解为全部部门 | 固定为无业务数据权限 |

### 4.2 推荐角色模板

| 模板 | 核心功能权限 | 默认业务定位 |
|---|---|---|
| 研发送样员模板 | 创建送样、编辑本人送样、确认本人退回 | 发起送样 |
| 分析检测员模板 | 待取样、取样、工作量录入、撤回本人取样 | 执行检测 |
| 分析检测组长模板 | 分析员权限、退回、审核、查看范围内人员记录 | 部门分析管理 |
| 部门统计查看员模板 | 查询统计、导出 | 只读统计 |
| 部门管理员模板 | 管理本部门用户和部门角色 | 本部门配置 |
| 系统管理员模板 | 全公司配置、审计、全公司数据 | 总部系统管理 |

### 4.3 部门角色示例

| 部门角色 | 来源模板 | 分析检测部门范围 | 研发送样部门范围 |
|---|---|---|---|
| 研究院-分析检测员 | 分析检测员模板 | 研究院 | 无 |
| 动保一部-分析检测员 | 分析检测员模板 | 动保一部 | 无 |
| 研究院-送样员 | 研发送样员模板 | 无 | 研究院 |
| 研究院-分析检测组长 | 分析检测组长模板 | 研究院、动保一部 | 研究院 |

### 4.4 创建和使用流程

管理员创建“研究院-分析检测员”角色：

1. 进入“角色与权限”。
2. 点击“从模板创建角色”。
3. 选择“分析检测员模板”。
4. 填写角色名称：`研究院-分析检测员`。
5. 在“分析检测业务部门范围”勾选“研究院”。
6. 保存角色。
7. 在用户管理中，为研究院分析人员勾选该角色。

## 5. 业务数据归属规则

### 5.1 必须区分的部门维度

跨部门业务不能只保存一个“部门”字段。每条相关记录必须明确保存：

| 字段 | 含义 | 写入时机 |
|---|---|---|
| 项目归属部门 | 项目主责部门 | 项目创建或维护时 |
| 送样部门 | 样品发起部门 | 创建研发送样时 |
| 执行部门 | 实际分析检测部门 | 由执行实验室确定 |
| 执行实验室 | 实际执行检测的实验室 | 送样/取样时确定 |
| 实际送样人 | 送样业务归属人员 | 送样提交时 |
| 实际取样人 | 取样业务归属人员 | 取样时 |
| 实际检测人 | 工作量归属人员 | 工作量录入时 |
| 操作账号 | 实际操作系统的登录账号 | 审计日志写入 |

### 5.2 跨部门示例

研究院项目送样至动保一部液相实验室：

| 维度 | 示例值 |
|---|---|
| 项目归属部门 | 研究院 |
| 送样部门 | 研究院 |
| 执行部门 | 动保一部 |
| 执行实验室 | 动保一部液相实验室 |
| 实际送样人 | 张三 |
| 实际取样人 | 李四 |
| 实际检测人 | 李四 |
| 操作账号 | 分析公共账号 |

### 5.3 各模块数据范围口径

| 模块 | 查询和权限的主要部门口径 | 可操作人员 |
|---|---|---|
| 研发送样 | 送样部门、项目归属部门 | 创建人、实际送样人、授权审核角色 |
| 待取样与取样 | 执行部门、执行实验室 | 分析检测员、分析检测组长 |
| 工作量录入 | 执行部门、执行实验室 | 分析检测员 |
| 样品信息登记 | 登记部门 | 登记角色 |
| 项目维护 | 项目归属部门 | 项目维护角色 |
| 分析统计 | 执行部门 | 分析统计角色 |
| 送样统计 | 送样部门 | 送样统计角色 |
| 项目统计 | 项目归属部门 | 项目统计角色 |
| 审计日志 | 操作部门和业务部门双维度 | 审计查看角色 |

## 6. 分析公共账号规则

### 6.1 改动前后

| 项目 | 改动前风险 | 改动后规则 |
|---|---|---|
| 人员选择 | 公共账号、实际人员和部门权限容易混淆 | 公共账号先选实际分析人员，再进入原业务页面 |
| 工作量归属 | 容易归属到公共账号 | 归属到已选实际人员 |
| 取样归属 | 容易归属到公共账号 | 归属到已选实际人员 |
| 审计日志 | 难判断谁实际点了操作 | 始终记录公共账号为操作人 |
| 可选人员 | 可能按实验室、部门或权限混合筛选 | 公共账号归属部门下的分析角色启用人员 |
| 业务范围 | 容易因选人扩大数据范围 | 仅由公共账号角色的数据范围决定 |

### 6.2 公共账号操作流程

```text
登录分析公共账号
  -> 显示原有“分析检测”和“样品信息登记”入口
  -> 点击“分析检测”
  -> 显示本公共账号归属部门下的分析人员卡片
  -> 点击实际人员
  -> 进入原有分析检测门户
  -> 进入实验室、研发送样记录或工作量录入
  -> 业务归属写入实际人员，审计写入公共账号
```

### 6.4 公共账号后端校验规则

1. 分析公共账号取样、录入工作量时必须提交实际人员 ID。
2. 后端确认该人员属于公共账号可选择人员范围，且账号处于启用状态。
3. 后端确认当前公共账号角色拥有对应业务部门数据范围。
4. 业务记录保存实际人员；审计日志保存公共账号。
5. 普通账号传入实际人员 ID 时，后端直接拒绝，防止伪造归属。

## 8. 功能改造清单

| 编号 | 改造项 | 改动前问题 | 改动后规则 | 涉及功能 |
|---|---|---|---|---|
| 1 | 部门主数据 | 名称、用途和范围可能不统一 | 部门为唯一数据隔离单位，增加编码、状态、负责人 | 组织架构、筛选、统计 |
| 2 | 实验室归属 | 实验室可能被当作人员分析组 | 每个实验室唯一归属执行部门 | 实验室管理、待取样、工作量 |
| 3 | 项目归属 | 项目与部门关系不明确 | 每个项目明确项目归属部门，可配置协作部门 | 项目、送样、统计 |
| 4 | 用户归属 | 用户、实验室、角色关系混杂 | 明确主部门、可承担业务部门、部门角色 | 用户管理、公共账号 |
| 5 | 角色模板 | 相近角色重复创建、维护困难 | 模板定义功能权限上限 | 角色管理 |
| 6 | 部门角色 | 角色和范围混在一起 | 部门角色 = 模板 + 部门数据范围 | 权限管理 |
| 7 | 业务范围 | 空范围和全范围含义不清 | 空范围无数据权限，全范围需明确配置 | 所有业务查询和操作 |
| 8 | 送样记录 | 单一部门字段无法支持跨部门 | 保存送样、项目、执行部门等多维归属 | 送样、退回、统计 |
| 9 | 取样记录 | 公共账号可能成为取样人 | 实际人员为取样归属，公共账号为审计人 | 待取样、取样、撤回 |
| 10 | 工作量 | 工作量可能归属公共账号或错误部门 | 实际检测人和执行部门明确保存 | 工作量录入、统计 |
| 11 | 统计导出 | 不清楚按哪个部门统计 | 提供送样、执行、项目三种统计口径 | 统计、导出 |
| 12 | 审计日志 | 无法区分代操作和业务归属 | 同时保存操作账号和实际业务人员 | 审计、追责 |

## 9. 数据库与接口改造要求

### 9.1 数据结构

| 数据对象 | 必须新增或规范内容 |
|---|---|
| 部门 | 部门编码、启用状态、排序、负责人 |
| 实验室 | `execution_department_id`，即唯一执行部门 |
| 项目 | `owner_department_id`，可选项目协作部门关联表 |
| 用户 | 主部门、可承担业务部门、多个部门角色 |
| 角色 | 模板来源、所属部门、可维护级别 |
| 角色范围 | 按业务域保存角色可访问部门 |
| 研发送样记录 | 送样、项目归属、执行部门和实验室快照 |
| 工作量记录 | 执行部门、实际检测人、操作人快照 |
| 样品登记记录 | 登记部门、项目归属部门、操作人快照 |
| 审计日志 | 操作账号、实际业务人员、业务部门维度、变更前后值 |

### 9.2 接口和后端要求

1. 所有列表查询接口必须接入部门范围过滤。
2. 所有新增、编辑、取样、退回、确认退回、撤回接口必须进行后端部门范围校验。
3. 所有导出接口复用列表查询的部门范围和统计口径，不能独立绕过过滤。
4. 公共账号接口必须校验实际人员候选范围、实际人员状态和业务范围。
5. 部门范围改变后，用户重新登录或刷新权限上下文后立即生效。

## 10. 历史数据迁移规则

1. 不覆盖历史记录已有字段。
2. 可通过项目、实验室、创建人可靠判断的部门字段进行自动回填。
3. 无法可靠判断的记录标记为“历史待确认归属”。
4. 提供管理员批量确认页面，不允许系统无依据猜测部门。
5. 统计页面提供“仅规范数据”和“包含历史待确认数据”筛选。
6. 历史记录的原始数据、迁移规则、迁移时间和操作人必须写入审计日志。

## 11. 实施阶段

### 第一阶段：基础数据治理

1. 统一部门名称、编码、状态和负责人。
2. 为每个实验室指定唯一执行部门。
3. 为每个项目指定唯一项目归属部门。
4. 梳理现有用户、角色和公共账号。
5. 形成旧角色到新角色模板、部门角色的映射表。

### 第二阶段：权限模型和后台页面

1. 新增角色模板。
2. 新增部门角色和按业务域的数据范围。
3. 改造用户管理页面。
4. 改造公共账号配置页面。
5. 后端统一接入三层权限判定。

### 第三阶段：业务记录归属

1. 改造研发送样、取样、工作量和样品信息登记记录。
2. 公共账号统一保存实际人员和操作账号。
3. 改造待办、列表、退回、撤回和确认退回的权限规则。
4. 补齐审计日志。

### 第四阶段：统计和导出

1. 每张统计表增加统计口径：送样部门、执行部门、项目归属部门。
2. 导出复用当前查询口径和数据范围。
3. 增加部门汇总、跨部门协作和历史待确认数据提示。

### 第五阶段：迁移和上线

1. 先在测试数据库执行历史数据迁移。
2. 输出迁移差异报告。
3. 由各部门负责人确认异常数据。
4. 先选择研究院和一个协作部门试运行。
5. 验收后逐步扩展至全公司。

## 12. 验收标准

1. 仅有研究院范围的角色，看不到动保一部未授权的实验室、记录、统计和导出。
2. 同时拥有研究院和动保一部范围的角色，可以处理两个部门范围内的业务，不能查看其他部门。
3. 研究院送样至动保一部后，研究院可查询送样，动保一部可查询待取样和执行记录。
4. 同一跨部门记录可按送样部门、执行部门、项目归属部门分别统计，且结果可追溯。
5. 分析公共账号选择李四后，工作量和取样归属为李四，审计日志操作人为公共账号。
6. 空数据范围的角色不能读取、导出、编辑或操作任何业务数据。
7. 通过修改前端请求参数不能绕过后端部门范围校验。
8. 导出结果不得包含当前角色无权访问的部门数据。
9. 历史待确认归属数据必须有明确标记，不能无提示混入正式部门统计。

## 13. 上线后的日常管理方式

### 新增部门

1. 在组织架构中创建部门。
2. 创建该部门实验室和项目归属。
3. 从模板创建该部门的分析、送样、统计等部门角色。
4. 为部门人员分配角色。
5. 如需要，配置部门公共账号和可选人员。

### 新增人员

1. 创建用户并设置主归属部门。
2. 如需跨部门协作，登记可承担业务部门。
3. 分配对应部门角色。
4. 如从事分析检测，系统自动按部门和分析角色纳入公共账号选人范围。

### 跨部门协作

1. 不通过临时扩大用户权限解决。
2. 应为协作岗位配置明确的跨部门部门角色或增加该角色的数据范围。
3. 协作结束后移除对应部门角色或收回范围。

### 权限审计

1. 每季度导出部门角色、人员角色和数据范围清单。
2. 由部门负责人确认在岗人员及跨部门范围。
3. 对离职、转岗、部门调整人员及时停用账号或调整角色。
