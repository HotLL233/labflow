# 开发验证与交付自动化

现行规则以根 PROJECT_MEMORY.md 为准。本页于2026-11-05更新：正式安装包只进入GitHub Release，
CI不再回写源码仓库；历史说明中的三处留存和旧命名只代表当时流程。

所有命令使用PowerShell 7，从本机实际项目目录执行。脚本相对路径按仓库根或脚本位置解析，
不固定盘符。`$sourceDir`必须明确选择本轮开发版本，不能靠最高文件夹推断正式版本。

## 1. 准备与版本检查

```powershell
$version = Read-Host '输入本轮开发版本 X.Y.Z'
$sourceDir = "source/LabFlow-PostgreSQL-v$version"
pwsh -NoProfile -File scripts/prepare-local-build.ps1 -SourceDir $sourceDir -InstallDependencies
pwsh -NoProfile -File scripts/check-version.ps1 -SourceDir $sourceDir -ExpectedTag "v$version"
```

新业务先从当前正式源码创建递增目录，排除缓存、运行库链接、安装包、运行数据和旧记忆。
九处版本文件的十二个字段须一致；应用包labflow与历史workload-tool按实际包身份识别，
不替换依赖包版本。三段数字无前导零，每段0..65535；Windows数字版本固定X.Y.Z.0。

新机先安装Git、PowerShell7、Node24、Rust stable MSVC/C++ Build Tools；本地出包另需Inno Setup6。
build-resources只有一份公共运行库；node_modules、target和junction在本机创建，不从旧机器复制。
共享依赖池不能直接npm ci，使用准备脚本按锁文件安装。

## 2. 验证层级

```powershell
pwsh -NoProfile -File scripts/test-automation.ps1
pwsh -NoProfile -File scripts/verify.ps1 -SourceDir $sourceDir -Profile Quick -OutputDir "test-artifacts/$version/quick"
pwsh -NoProfile -File scripts/verify.ps1 -SourceDir $sourceDir -Profile Build -OutputDir "test-artifacts/$version/build"
```

- Quick：版本、前端测试和类型检查、Rust格式/编译检查。
- Build：增加前端生产构建/gzip/静态核验与Rust Release。
- Integration：Build基础上执行数据库库测试，必须显式提供隔离测试库环境变量及
  `-AcknowledgeIsolatedDatabase`；不能用生产连接串。Windows测试库数据目录用ASCII路径。
- 可用`-Component Frontend/Backend`做单侧检查，默认All；正式出包要求当前All Build/Integration报告。

报告记录Git修订、受控输入、产物哈希和实际状态。数据库、HTTP/Excel、浏览器/手机、
现场升级、容器运行和真实云盘/机器人未执行时必须标not_run。
工具/工作流、源码或锁变化后旧报告失效；本机有缓存不等于冷下载验收。
失败与修复记录保留，不把失败轮次改写成干净通过。

前端验证产物输出在独立报告目录，不覆盖已发布版本的backend/static。
新版本通过生产构建后，将本版生产静态资源随本版源码提交；旧版本不覆盖。

## 3. 从同一已验证产物生成两包

```powershell
$env:INNO_SETUP_ISCC = Read-Host '输入本机ISCC.exe实际路径（已可自动检测时可留空）'
pwsh -NoProfile -File scripts/build-installers.ps1 -SourceDir $sourceDir `
  -VerificationReport "test-artifacts/$version/build/verification.json" `
  -OutputDir "test-artifacts/$version/packages"
```

可用`-IsccPath`或环境变量指定实际位置，工具也会探测已有安装；不要照搬历史D:/APP或其他机器路径。
打包复用报告中的Release与独立静态产物，验证输入、哈希及ISCC每次退出码；已有同名包时拒绝覆盖。
根build-resources提供PDF/PostgreSQL/VC运行库/安装语言，不能删除当前公共资源。

新完整包为`labflow-vX.Y.Z.exe`；新热更新包为`labflow-vX.Y.Z-hotupdate.exe`，只升级已有完整服务器安装。
内嵌产品/文件版本X.Y.Z.0，产品labflow、发布者HotLL；程序内既有品牌和自定义配置不改。
输出manifest.json、SHA256SUMS和交付清单；Release使用ASCII名DELIVERY-CHECKLIST.md。
本地验证包、CI预验收包与CI正式包分别记来源/哈希，不因相同版号就视为相同二进制。

## 4. 正式发布

1. 检查真实需求相关功能、权限、统计、历史兼容及自定义配置；只提交本轮授权源码和文档。
2. 完成验证、预验收和安装包检查后，推送main，创建并推送不可移动的注释标签vX.Y.Z。
3. Windows/Docker先运行共享工具测试、严格版本和发布策略检查，再按该标签明确源码目录构建。
4. Windows两包与三份交付文件进入对应Release；不再回写installers目录。Docker进入GHCR版本标签和latest。
5. 核对两个工作流、标签源码、Release/两包摘要、GHCR版本和latest；正式包取回本地核对后，
   再更新共享记忆和版本状态。只推源码、只生成CI Artifact不等于正式交付完成。

发布策略由scripts/release-policy.cjs统一检查：

- 严格三段版本、注释标签和运行SHA；拒绝移动标签。
- 对照GitHub标签/Release及GHCR标签最大版本，拒绝旧版本回退。
- 已存在的Windows Release或镜像版本不覆盖；metadata请求失败时停止发布。
- 按渠道串行，Windows发布前再次核对；Docker只允许正式标签事件推送。
- 软件发布工作流的手动workflow_dispatch只验证/预验收，不创建正式Release、不推镜像、不更新latest。
- 手动验证选main或包含新策略的开发分支作为workflow ref，不指定冻结的旧标签加载旧工作流。
- 首次发布某渠道失败且未生成其正式资产时，可在原标签原源码上重试；修改受控输入则须递增版本。
- 已发布旧标签携带旧工作流，不自动获得main新保护；不得直接重跑旧版发布或使用已弃用重发入口。

新仓库规范以Release为软件分发入口。不要重写历史、强推或移动旧标签；
不要把先前保留在main历史目录的运行库当成新版本构建依赖来源。

## 5. 诊断与历史资料

- repository-checks.yml在Windows和Ubuntu执行共享自动化测试，不编译/发布软件，不访问业务数据库。
- CI Artifacts是临时证据；发布验收结论、源码与哈希写入共享记忆、版本说明和Release清单。
- 私有test-artifacts保留详细过程；仓库只保存脱敏摘要，不上传原始聊天、凭据或真实业务数据。
- 历史过程、失败轮次和旧惯例保留在docs/history；发布状态和异常见docs/releases索引。
- 此次仓库治理不改变v2.4.7软件版本，不声称重新执行其391项后端或现场安装验收。
