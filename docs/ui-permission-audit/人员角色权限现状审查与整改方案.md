# 人员、角色与权限：现状审查与整改方案

实施记录：[v2.4.13 实施与验证对照](../ui-method-treatment/v2.4.13-实施与验证对照.md)。下文保留方案和旧版基线，最终实现、验证及交付状态以实施记录和版本安装包说明为准。

日期：2026-11-12。基线：根README指定正式版v2.4.12。本文为待实施方案，仅分析源码，没有修改角色、用户、业务数据或正式软件。

**当前并非只有角色勾选框决定权限。**实际可操作范围还取决于多角色合并、系统身份、部门和样品类型范围、本人/创建者关系、组长职责以及记录状态。应先让这些规则可见，再修复确实不一致的入口和保存逻辑；无需重做一套权限系统，也不应重置现有配置。

[打开 HTML 参考](LabFlow-角色与实际权限参考.html)。包含角色功能与范围、成员实际权限、入口/API 对照及保存差异预览。全部为合成数据与内存模拟；正式的实际权限解释必须由服务端授权规则产生。

## 1. 当前实际授权如何产生

| 层次 | 当前规则及证据 | 管理页应如何解释 |
| --- | --- | --- |
| 账号状态、登录会话 | JWT签名和服务端会话均检查，停用账号被拒绝；每次常规鉴权再从数据库读取用户和权限。[auth_service.rs:124](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/auth_service.rs:124)、[authz_service.rs:148](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/authz_service.rs:148) | 显示账号启用状态。JWT含登录时权限，但不是后端授权的唯一事实来源 |
| 角色功能权限 | `user_roles`各角色的权限并集、去重；仅在没有多角色关联时回退旧`users.role_id`。[user_repo.rs:299](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/user_repo.rs:299)、[user_repo.rs:567](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/user_repo.rs:567) | 同一能力列出全部授予角色；取消一个角色的勾选，不代表另一个角色的授予消失。当前没有独立的用户权限覆盖表/直接授权维护流程 |
| 管理员与通配 | `is_admin`或`*`使普通权限命中；部分敏感动作另外要求真实系统管理员，不能把`*`等同于所有管理员业务身份。[authz_service.rs:39](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/authz_service.rs:39)、[role_handler.rs:130](../../source/LabFlow-PostgreSQL-v2.4.12/src/api/role_handler.rs:130) | 显示“系统管理员放行”或“角色通配授予”，并说明仍受专属身份/安全规则约束。管理员身份是预期规则，不作为漏洞 |
| 业务身份 | 公共账号按稳定`system_key`判断；组长还按内置角色名或来源模板名判断。[authz_service.rs:61](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/authz_service.rs:61) | 单列“研发组长/分析组长/公共账号”等只读身份及来源；普通权限勾选不会自动赋予组长职责 |
| 数据范围 | 分析部门范围、研发来源部门范围、样品登记类型范围分开；样品登记保留每个角色自己的“部门与类型交集”，角色之间再取允许结果的并集。[authz_service.rs:176](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/authz_service.rs:176)、[authz_service.rs:535](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/authz_service.rs:535)、[authz_service.rs:760](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/authz_service.rs:760) | 显示角色范围明细，不能把A角色的部门与B角色的类型交叉拼成扩大后的范围；当前范围汇总接口只供隐藏界面，不等同于完整授权解释 |
| 人员归属与记录关系 | 主部门、业务部门、实验室、创建账号和实际业务人员不是一个概念。样品登记编辑同时要求`sample-info:edit-own`、记录可访问、本人创建或本人为业务人员，且记录尚未取样。[user.rs:10](../../source/LabFlow-PostgreSQL-v2.4.12/src/models/user.rs:10)、[sample_info_handler.rs:580](../../source/LabFlow-PostgreSQL-v2.4.12/src/api/sample_info_handler.rs:580) | 显示“本人创建/本人送样”等范围依据，不用人员姓名猜身份。公共账号操作人和真实送样人分开呈现 |
| 页面和动作状态 | 导航是否启用、路由、页面按钮、服务端接口及记录状态分别控制可用性。[ProtectedRoute.tsx:23](../../source/LabFlow-PostgreSQL-v2.4.12/frontend/src/components/ProtectedRoute.tsx:23)、[ManageNav.tsx:126](../../source/LabFlow-PostgreSQL-v2.4.12/frontend/src/components/ManageNav.tsx:126) | 区分“入口隐藏”“缺少功能权限”“数据不在范围”“记录状态禁止”，不能统一显示为“无权限” |

前端会从`/api/users/me`刷新用户信息，权限修改、用户角色/归属调整会撤销相关会话。菜单短时未刷新不等于后端继续放行；同样，看到菜单也不能证明接口可用。[UserContext.tsx:70](../../source/LabFlow-PostgreSQL-v2.4.12/frontend/src/UserContext.tsx:70)、[role_repo.rs:484](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/role_repo.rs:484)、[user_repo.rs:861](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/user_repo.rs:861)。

导航配置可控制显隐，但不是授权。直接访问地址、请求详情/附件/导出都必须继续由服务端校验。现有管理导航共用`MANAGE_NAV_GROUPS`是可复用基础，不另复制第三套菜单表。

## 4. 建议的页面方案

保留“用户”和“角色与权限”原入口，不改变日常业务门户。角色页继续一张角色列表，详情使用三个清楚的区域。

### 4.1 角色功能与范围

- **功能权限**：按研发送样、样品登记、分析检测、辅助工作、统计、通知与系统维护分组。每项显示动作说明和状态；code收在详情中。搜索、仅已选继续保留。
- **数据范围**：把“分析检测部门”“研发来源部门”“样品登记类型”分列，解释空范围的真实含义。不要统一用“未选＝全部”；不同业务当前有不同兼容行为，显示实际规则。样品登记按单角色交集、角色之间并集展示。
- **规则说明**：系统必需内部项、管理员专属动作、组长职责、历史兼容项均可见，分别标“只读必需”“身份限定”“兼容不生效”。普通业务权限可取消且持久保留撤销。

保存前列出本次新增/撤销动作、范围变化、受影响成员数以及是否撤销登录会话。功能和范围一次事务保存；拒绝时保留输入、原因及当前服务端修订，不能部分保存后仍声称完全未生效。

### 4.2 从用户查看实际权限

在用户列表原操作处增加“查看实际权限”，不再新增一套人员授权页。选中用户后展示账号状态、角色、公共账号/组长身份和实际范围；下表按功能列出结果、来源、缺失条件。

| 功能示例 | 结果 | 依据/原因示例 |
| --- | --- | --- |
| 工作量录入 | 允许 | 角色“分析检测员”授予`entry:workload`；可用部门为当前授权范围 |
| 仪器维护 | 不允许 | 方法管理已授予，但没有`manage:instruments` |
| 角色配置保存 | 不允许 | 仅有`manage:roles`可查看；当前账号非系统管理员 |
| 人员变动审批 | 不允许 | 查看/编辑已授予，但不具分析组长职责；不能据此通过另一个开关绕过 |
| 公共账号选检测人 | 受限允许 | 公共账号身份带系统必需开关；候选人仍限指定部门与原授权 |

该页由服务端使用同一实际授权规则给出解释；前端不自行计算一套“看起来有效”的权限。先实现上述关键能力解释与角色来源，不引入通用策略引擎、用户级覆盖/拒绝规则或自动推测权限。

需要区分“具备功能能力”和“可对某条记录操作”。涉及具体对象时提供“此记录为何不可维护”的原因：缺功能权限、超出部门/类型范围、不是创建者/业务人员、记录已取样等。查询解释仍需管理权限并限制返回内容，不额外读取越权业务记录或暴露凭据。

### 4.3 统一权限目录和依赖说明

以服务端白名单为权威目录，前端本地定义由受控生成或一致性检查同步；只补充模块、说明、依赖、系统必需/兼容状态等必要元数据，保留所有现有permission key。

对于“仅勾导出缺统计入口”“有方法管理无仪器维护”“有人员编辑无组长职责”等情况，保存前给出明确说明，不静默勾选别的权限。影响已有可见范围的变更只预览，不自动扩大，也不从历史角色模板重新覆盖管理员配置。

## 5. 实施顺序和保留规则

1. 先修R01、R02：撤销应持久，保存必须完整，避免边整理UI边产生新的授权混乱。
2. 修仪器、帮助、辅助页等已证实的入口依赖；同步菜单、路由、按钮、API实际要求，并保留管理员/组长职责边界。
3. 增加清楚的模块分组、只读规则、历史兼容标记及有效权限解释；继续使用原角色/权限/数据范围表。
4. 加目录一致性与代表性入口/API契约检查。对剩余API逐批补对照，未覆盖部分不能标为全部通过。

不重置内置/自定义角色，不重命名或删除已有code，不恢复旧部门角色体系，不新增个人直接授权，不按角色显示名猜现有身份，也不以“功能更好用”为由扩大读取或维护范围。管理员专属动作保持现有保护；现有历史记录、系数、实际人员、来源链、统计口径和自定义布局不变。

## 6. 最小真实验收矩阵

| 检查 | 必须结果 |
| --- | --- |
| 分析组长取消通知管理后重启两次 | 不再自动补授；管理员自己的预期身份能力仍保留；迁移幂等 |
| 权限＋范围一项非法/中途失败 | 整体拒绝，无半份配置、无误报成功；输入可修正后重试 |
| 管理员修改包含自身的角色 | 保存和会话变更顺序明确，不因两个请求竞争留下半成功 |
| 两名管理员同时编辑一个角色 | 旧修订拒绝并显示冲突，不能静默覆盖对方变更 |
| 多角色A授予、B也授予同一能力，取消A | B仍有效，解释显示剩余来源；取消全部才撤销 |
| 普通manage:roles和普通`*`角色 | 可以按现行规则查看/命中普通能力；管理员专属授权动作仍被服务端拒绝 |
| 分析公共角色保存空普通权限 | 系统必需开关按既有业务要求保留，页面明确显示；不附带授予其他普通功能 |
| 仅方法管理 / 仅仪器管理 / 两者都有 | 分别只读或可写、入口可达；直接写API行为与按钮一致 |
| 帮助阅读角色 / 普通帮助管理角色 / 管理员 | 阅读、拒绝原因、维护入口与服务端一致，不因修UI开放管理员专属写入 |

| 样品创建者、实际业务人员、无关人员 | 原维护范围、取样状态保护及编辑权限保留；不靠姓名推断本人 |

| 菜单隐藏后直接访问路由/详情/附件/导出 | API仍按功能、范围、身份、对象状态拒绝；菜单隐藏不替代授权 |
