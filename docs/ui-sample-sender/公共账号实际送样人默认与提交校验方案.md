## 2. 如何可靠识别公共账号

当前已存在两个可靠标识：

- 服务端按角色稳定 `system_key` 判断：`public_account` / `rd_public_account` 为研发公共，`analysis_public_account` 为分析公共。见 [authz_service.rs:85](../../source/LabFlow-PostgreSQL-v2.4.12/src/service/authz_service.rs:85)。
- 会话中公开 `is_rd_public_account`、`is_analysis_public_account`；旧 `is_public_account` 只等于研发公共，不能把它当作所有公共账号的总标记。见 [user_repo.rs:234](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/user_repo.rs:234)、[types/index.ts:643](../../source/LabFlow-PostgreSQL-v2.4.12/frontend/src/types/index.ts:643)。

样品登记中的默认行为应对研发公共、分析公共取并集。前端只用会话标识决定初值与提示；提交时服务端仍重新按真实账号及角色判断，不能信任浏览器上传的“个人/公共”状态。

**不能仅凭账号叫“厂区送样人员”、角色显示名包含“公共”来判定。**未读取现场账号配置，尚不能确认这些实际账号是否拥有上述稳定公共角色。上线前应核对其账号类型：已有公共标识的直接适用；若是自定义共享账号但没有上述标识，在账号维护中增加明确的“实际送样人必须手填”设置，并由服务端公开只读会话能力。该设置只决定真实送样人录入要求，不给账号增加角色、入口或数据范围；不为了清空初值而强行授予一个业务公共角色。不要按昵称批量猜测回填。

## 3. 最小完整调整

### 表单与草稿

1. `emptyRow` 统一处理：公共账号的 `user_name=''`，个人账号仍为本人用户名。公共账号显示“请填写实际送样人”，登录提交账号单独显示为只读上下文；不新增人员选择层级，不要求送样人一定有系统账号。
2. 加行、重置、删空后的新行、全部提交成功后的新行复用上述规则。成功记录移除，失败行连同实际送样人和附件继续保留；不把上一条填写的人名自动复制到下一条新记录。
3. 公共账号提交逐行校验去首尾空白后的实际送样人；空值明确提示“第X行请填写实际送样人”，聚焦该行。去掉 `row.user_name || '未知'` 的补值。用户确实填写的自由文本按现有规则保存，UI占位不作为真实数据发送。
4. 动态列将送样人设为非必填也不能关闭这条公共账号校验。若当前类型隐藏了该原生字段，界面应提供同一原生字段的补录位置或明确提示配置冲突；不能出现接口要求填写、界面却无处填写的情况，也不修改管理员持久配置来伪装兼容。
5. 保存草稿允许送样人为空；恢复后仍需通过提交校验。新草稿可保存“已由使用者确认”的状态用于恢复提示，不能把数值非空当成确认依据。旧草稿的“未知”、空白或与当前公共账号名相同的值显示为待确认；让使用者重新填写/确认后再提交。其他行、附件和未提交信息保留。
6. 不把与公共账号名相同的文字永久列入姓名黑名单。确有同名人员时允许明确重新输入；不能仅凭同名字串推断人不是实际送样人。旧草稿的可疑自动值与已提交历史分开处理，后者不自动清空。
7. 当前会话组件按账号ID和令牌挂载，见 [SampleInfoEntry.tsx:1775](../../source/LabFlow-PostgreSQL-v2.4.12/frontend/src/pages/SampleInfoEntry.tsx:1775)。继续保留账号切换隔离，不将上一登录账号的人员草稿带给另一账号。

### 服务端统一规则

将“解析实际送样人”作为两个创建入口共用的校验：

| 请求 | 处理 |
| --- | --- |
| 公共账号，实际送样人缺失、空白或明确UI占位 | 拒绝创建，提示填写；不回退公共账号名、不写“未知” |
| 公共账号，明确填写了真实姓名文本 | 去首尾空白后按当前自由文本规则保存，不强制账号绑定 |
| 个人账号，省略实际送样人 | 保留现有兼容：使用本人登录名 |
| 个人账号，已填写其他实际送样人 | 按原有规则处理，本轮不额外授予代填权限或扩大数据范围 |
| 草稿保存 | 允许不完整；实际创建时才做完整提交校验 |

普通创建和带附件创建使用同一规则。附件请求在正式记录/附件元数据落库前拒绝，错误不能留下有效记录或发出送样通知；保留现有事务、附件清理及提交结果不确定的处理，不另造一条绕过它们的创建路径。

当前多行提交是前端顺序发单条请求，不存在这条页面专用的批量创建API。应保留已成功/失败行的精确反馈，不声称实现了整批原子事务，也不能因重试把已成功行再次发送。

## 4. 身份、权限、通知与历史

“实际送样人文本”和“提交操作者”继续分开：`user_name` 保存实际送样人；`created_by_user_id`、`created_by_username_snapshot`、审计operator继续保留真正登录提交账号，见 [sample_info_repo.rs:838](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/sample_info_repo.rs:838)。不能用填写的人名替换登录操作者，不能因实际送样人留空改变取样人、检测人或工作量人员。

还需明确当前的既有行为：创建及改变送样人时，库会按 `user_name` 精确查找账号生成 `business_user_id`，未匹配时回退创建账号；它不是单纯的展示字段。见 [sample_info_repo.rs:772](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/sample_info_repo.rs:772)、[同文件:1081](../../source/LabFlow-PostgreSQL-v2.4.12/src/repo/sample_info_repo.rs:1081)。当前本人编辑授权也接受真实创建者或业务人员，见 [sample_info_handler.rs:583](../../source/LabFlow-PostgreSQL-v2.4.12/src/api/sample_info_handler.rs:583)。本轮只防止默认误填，不借此重建人员身份或更改现有归属；不能把自由填写姓名宣称为精准账号身份验证。此关联如何影响“本人”范围，应在权限审查页面明确显示规则，另行决定是否调整。

历史已提交记录不按当前账号名、相似姓名或新规则自动改写。普通编辑继续按原权限和取样状态维护；未提交 `user_name` 的日期/备注编辑保留原值。显式更改实际送样人时校验新值并保留前后审计，不能将新建初值规则用于清空历史。退回记录保留原来源、组织和序号关系，重新提交时明确核对实际送样人，不把原记录复制成一条无关联新记录。

通知继续在成功提交后使用最终保存的 `user_name`。提交账号仍独立用于操作追溯；不能直接根据手填自由文本扩展通知接收范围或精准@绑定，不能将“填写送样人”当成授权证明。校验失败不能发送成功通知。

## 5. 导入与恢复边界

后台数据治理导入不是上述页面创建：它在 [data_governance_handler.rs:1186](../../source/LabFlow-PostgreSQL-v2.4.12/src/api/data_governance_handler.rs:1186) 调用 `find_user`；该函数在 [同文件:1013](../../source/LabFlow-PostgreSQL-v2.4.12/src/api/data_governance_handler.rs:1013) 允许空值、但对非空且查不到有效账号的名称报错。之后在 [同文件:1469](../../source/LabFlow-PostgreSQL-v2.4.12/src/api/data_governance_handler.rs:1469) 直接插入数据。这与自由填写表单的人员规则并不相同。本轮不为默认留空要求顺带放宽管理员导入权限、取消已有导入校验或猜测历史人员关联。

数据治理导入应在预览中说明送样人缺失/占位及未匹配的原因，不能补成当前公共账号；需要补录新业务时明确填写。备份恢复保持备份中的原人员、操作者和来源事实，不用当前登录公共账号替换旧值。旧历史质量问题如需修正，先独立预览和人工确认，不全库回填。
