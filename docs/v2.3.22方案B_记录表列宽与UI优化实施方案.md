# v2.3.22 记录表列宽与 UI 优化实施方案（方案 B）

> 本文是后续代码优化的唯一实施依据。目标是在保留 v2.3.19 列宽稳定性的基础上，逐步引入 v2.3.22 的最小宽度保护、操作列收纳、配置闭环和响应式能力。实施过程中按阶段验收，不得一次性叠加所有 UI 改动。

## 1. 背景与目标

### 1.1 背景

v2.3.19 的记录表主要采用固定表格布局和按权重归一化的百分比列宽。布局链路较短，不依赖容器测量，因此列宽表现稳定，不容易出现极窄列或表头逐字换行。但它会压缩长文本列，后台配置值不一定等于最终像素宽度，操作列也可能占用过多空间。

v2.3.20 之后增加了容器测量、内容宽度测量、后台自动/自定义模式、本机拖拽和操作列收纳。功能增多后，`adaptiveColumns.ts` 与 `recordTableLayout.ts` 并存，容器宽度、选择列和整体压缩等因素使部分页面出现列宽异常。v2.3.22 已有长表头折算与最小宽度保护，应保留这些安全措施，但还需统一页面实现及设置生效链路。

### 1.2 目标

1. 恢复 v2.3.19 的稳定、可预测布局基线。
2. 避免任何列被压缩到不可读宽度，长表头不逐字竖排。
3. 在空间不足时优先压缩可压缩列、收纳操作，并在必要时横向滚动，不牺牲最小可读宽度。
4. 明确列宽来源及后台配置、本机拖拽的优先级。
5. 保持既有权限、状态判断、排序、筛选、编辑、附件和分页业务行为不变。
6. 分阶段实现，每阶段可独立验证、打包和回退。

### 1.3 非目标

本方案第一轮不做以下改动：

- 不调整数据库表结构，不新增 `list_label`、列优先级、字段合并等配置字段。
- 不合并部门、实验室、项目等语义列。
- 不重写业务权限或记录状态流转。
- 不同时重构导出列宽、通知文案或录入表单宽度。
- 不以隐藏列作为桌面端第一阶段的空间解决手段。

## 3. 统一产品规则

### 3.1 列宽来源优先级

```text
本机拖拽覆盖 > 后台自定义宽度 > 自动内容宽度 > 系统默认值
```

具体要求：

1. 本机拖拽只覆盖当前用户、当前表格，不影响其他用户。
2. 后台自定义宽度作为该字段的明确宽度，不得被自动缩放到小于最小可读值。
3. 自动宽度可以根据字段类型和当前可见内容估算，并受最小值、最大值约束。
4. 没有内容样本、容器宽度尚未获得或配置读取失败时，必须回退到稳定默认值，不得使用 0 作为真实表格宽度。
5. 恢复单列或整表本机宽度后，回到后台配置或自动宽度，不删除后台已保存值。

### 3.2 宽度分配规则

1. 每个占据表格水平空间的列都必须进入同一次布局计算，包括选择列、序号列、数据列、附件列和操作列。
2. 固定列、后台自定义列及本机自定义列必须有清晰宽度边界。
3. 有剩余宽度时，优先分配给主要成分、注意事项、方法、样品批号等长文本或识别关键字段，不做所有列等比例扩展。
4. 空间不足时，只能按各列“高于最小值的可压缩余量”分配压缩量；禁止按当前宽度对所有列做无下限整体缩放。
5. 列达到最小宽度仍无法放入容器时，保留最小宽度并出现横向滚动。横向滚动是可接受的兜底，不是布局失败。
6. 本机或后台明确自定义的列不得被自动压缩；因此造成溢出时，保留宽度并提示用户可横向滚动或恢复宽度。
7. 列顺序、隐藏状态和权限逻辑仍由现有数据和页面控制，宽度引擎不得擅自重排字段。

### 3.3 推荐字段宽度基线

以下为桌面端初始建议值，最终值需与当前字段内容和现有后台配置核对。后台配置优先；表中数值用于缺省值或验收参考，不可无条件覆盖已有用户配置。

| 字段类型 | 建议最小宽度 | 建议默认/目标宽度 | 备注 |
|---|---:|---:|---|
| 选择框 | 使用 `checkbox_column_width` | 配置值 | 没有选择能力的表不渲染占位列 |
| 序号 | 使用 `seq_column_width`，默认约 56px | 配置值 | 不得被压至表头折字 |
| 数量 | 64px | 68–76px | 数字居中或右对齐沿用现有风格 |
| 状态 | 82px | 90–100px | 状态文案必须完整可辨 |
| 日期时间 | 120px | 130–160px | 可按既有格式换行，不截断关键时间 |
| 送样人 | 72px | 80–100px | 具体受姓名长度影响 |
| 部门 | 90px | 100–140px | 不在第一阶段与其他组织字段合并 |
| 实验室 | 100px | 110–150px | 不在第一阶段与其他组织字段合并 |
| 项目 | 110px | 130–180px | 有剩余空间时可扩展 |
| 样品批号 | 112px | 124–160px | 关键识别字段，优先保障可读性 |
| 方法 | 112px | 140–220px | 长文本，允许两行展示 |
| 主要成分 | 160px | 180–260px | 长文本，优先扩展，最多两行 |
| 注意事项 | 160px | 170–260px | 长文本，优先扩展，最多两行 |
| 退回原因/状态说明 | 160px | 180–280px | 长文本，最多两行，完整内容可查看 |
| 附件 | 80px | 86–100px | 操作入口不得被裁剪 |
| 操作 | 依屏宽采用 96–160px | 按操作档位 | 不允许无限增长 |

## 4. 方案结构：保留稳定性，分阶段增加能力

### 4.1 列宽引擎职责

目标是让所有记录表使用同一套像素约束布局能力。建议以 `recordTableLayout.ts` 为记录表统一布局入口，并保留 `adaptiveColumns.ts` 供尚未迁移的录入表格或兼容页面使用。第一阶段不得贸然删除旧工具；先搜索全部调用点，确认没有其他页面依赖后，再决定是否标记弃用或清理。

记录表的布局输出至少需要能表达：

- `width`：最终列宽。
- `minWidth`、`maxWidth`：列宽约束。
- `source`：`local`、`admin`、`auto` 或 `default`。
- `wrap`：是否允许换行及其行数策略。
- `resizable`：是否允许本机拖拽。
- `overflow`：整表是否超出容器。

如果当前布局结果类型已有等价字段，应复用现有结构，不为命名一致而进行无必要重构。

### 4.2 容器宽度测量

1. 保留 callback ref 和 `ResizeObserver` 的挂载后测量方式。
2. loading 分支卸载表格时，表格重新挂载必须能再次获得实际容器宽度。
3. 容器宽度为 0 或尚未测得时，使用与页面布局相符的视口估算值或安全默认值；估算仅用于首屏，真实值获得后立即重新计算。
4. 监听容器尺寸变化，而非只监听窗口 resize。
5. 测量对象应是实际可用于表格的内容容器，不能把侧栏、工具栏或页边距重复扣除。
6. 不得因 `ResizeObserver` 更新导致无限渲染或列宽持续抖动。

### 4.3 长表头规则

1. 表头允许最多两行展示，禁止按单字断行造成竖排。
2. 长表头宽度估算按两行预算，不得以整句单行宽度挤占整表。
3. 表头使用原始完整字段名作为 `title` 或等价提示，折行不丢失完整名称。
4. 短表头在最小宽度内保持单行优先。
5. 如浏览器/CSS 设置会导致任意字符断行，应明确约束 `word-break`、`overflow-wrap` 和 `white-space`，并验证中文表头表现。

### 4.4 长文本单元格规则

1. 批号、方法、主要成分、注意事项、退回原因等使用统一的长文本样式。
2. 默认最多显示两行，超出部分省略；悬停或点击可查看完整内容，沿用项目已有 Tooltip/Popover 模式。
3. 不使用不明显的单元格内部滚动条作为常规展示方案。
4. 行内编辑输入框应跟随实际列宽，不能继续采用与列宽冲突的硬编码宽度。
5. 后台配置行高不能裁掉必需显示的两行文字。实际行高至少满足配置高度与两行内容高度中的较大值。
6. 附件、按钮、状态徽标等交互内容不能被长文本截断样式误伤。

## 5. 操作列 UI 方案

### 5.1 三档显示

操作列按实际表格内容容器宽度切换，阈值作为首轮默认值，实施时应结合现有 `computeActionColumnLayout` 规则及页面断点验证。

| 内容容器宽度 | 建议展示 | 建议列宽 |
|---|---|---:|
| ≥ 1400px | 一个主操作、少量常用次操作、其余进入“更多” | 150–160px |
| 1024–1399px | 一个主操作/图标操作 + “更多” | 112–128px |
| < 1024px | 一个主操作 + “更多” | 96–112px |

操作列不得因为可显示按钮数量变化而无限扩宽。`full` 模式仍用于需要旧式全部按钮展示的用户或运维排查，默认推荐 `auto`。

### 5.2 主操作选择

主操作应依据当前状态和现有业务判断选出，不可仅取操作数组中的第一个，也不可复制或重新实现权限判断。

建议交互示例：

- 样品信息登记：待取样时突出“取样”；待检测时突出“完成检测”；已取样时突出“录入工作量”；其他合法动作收纳在“更多”。
- 研发送样：待取样时突出“取样”；已取样时按现有权限突出“录入工作量”或“撤回取样”；退回状态突出“确认退回并修改”；其他动作进入“更多”。

最终主操作必须以各页面当前真实状态及权限代码为准，不得因本方案擅自新增、删除或改变动作。

### 5.3 菜单行为

1. 菜单动作顺序应保留原页面/后台顺序。
2. 现有权限禁止的动作按现有页面约定隐藏或禁用；若要改成“置灰并说明原因”，须单独确认并在各表统一，不属于第一阶段。
3. 菜单点击、键盘操作、焦点和关闭行为应遵循项目已有组件模式。
4. `auto` 与 `full` 模式切换不改变业务操作可用性，只改变呈现位置。

## 6. 后台表格配置闭环

### 6.1 统一读取

记录表的下列通用设置应通过 `useTableConfig.ts` 或当前项目已经存在的统一 hook 读取，不在各页面分别散落读取逻辑：

- `row_height`
- `seq_column_width`
- `checkbox_column_width`
- 已有操作列模式/密度设置（如适用）

规则：

1. 读取成功时应用后台值。
2. 读取失败或字段缺失时应用安全默认值。
3. 设置更新后应触发相应表格重新计算或刷新。
4. 无选择列的表格不得因 `checkbox_column_width` 产生空白占位。
5. 序号列宽不得只存在于配置状态而未反映到实际 `colgroup`、表头和单元格。
6. 行高配置不得导致长文本或操作按钮被裁切。

### 6.2 后台列编辑 UI

自动/自定义模式应清晰表达：

```text
列表宽度
(●) 自动（按内容）
    当前建议宽度：124px
( ) 自定义宽度
    [ 160 ] px
    [恢复自动宽度]
```

要求：

- 自动模式下，自定义数值输入不误导为当前实际生效宽度。
- 自定义模式下显示实际自定义 px 值。
- 如果当前尚无可测内容，不得伪造“实测值”；可显示系统建议值或“首次加载后计算”。
- “恢复自动宽度”切换模式但不破坏可恢复的历史值，具体保存策略沿用当前 API/数据模型。
- 整表恢复自动须有明确作用范围和确认反馈。
- 说明文案统一表达为：自动模式依据内容和字段类型估算宽度；空间不足时优先保护最小宽度，必要时横向滚动。不要把单元格内滚动描述为正常解决方式。
- 样品信息自定义列和 RD 列配置的术语、单位、保存反馈保持一致。

### 6.3 配置兼容

1. 现存 `width_mode`、`min_width`、`max_width` 配置优先兼容，不新增数据库字段。
2. 老数据没有 `width_mode` 时，应定义并测试兼容默认值，不可假设所有旧宽度都应自动或自定义。
3. API 请求类型、前端表单、持久化和记录表消费端必须保持同一字段语义。
4. 表单输入宽度、记录表显示宽度、导出列宽是不同用途，不能因本方案混用。

## 7. 前台列设置与本机宽度

### 7.1 列设置菜单示例

```text
┌────────────────────────────┐
│ 列设置（12/14）             │
│ 2 列未显示                  │
│ 当前有横向溢出，可横向滚动  │
│ [恢复全部默认宽度]          │
├────────────────────────────┤
│ ☑ 序号       自动 58px      │
│ ☑ 送样人     自动 72px      │
│ ☑ 样品批号   本机自定义 148px│
│ ☑ 主要成分   后台自定义 200px│
│ ☐ 附件       已隐藏          │
└────────────────────────────┘
```

### 7.2 本机拖拽规则

1. 继续使用当前按用户和表格隔离的本机存储键，不改变已有键格式，除非先提供迁移方案。
2. 拖动后立即应用并持久化；刷新后仍有效。
3. 用户拖宽某列时，不得自动压窄其他列来抵消宽度；可以增加表格总宽并横向滚动。
4. 双击列边界恢复该列后台/自动宽度；列设置菜单也提供单列恢复入口（若当前组件能力允许）。
5. 恢复全部只清除当前用户当前表格的本机覆盖，不删除后台配置。
6. 本机值在 UI 中标记为“本机”，后台值标记为“后台”，自动值标记为“自动”。
7. 拖拽手柄不可意外触发表头排序、筛选、行点击；支持可访问焦点和足够命中区域。

### 7.3 溢出提示

当最终表格宽度大于可用容器宽度时，显示不遮挡操作的轻提示，例如：

```text
当前列宽超过可视区域，可横向滚动查看。 [恢复默认宽度]
```

提示应在溢出消失时自动隐藏；不得在每次渲染重复弹出 toast。

## 8. 窄屏行为

窄屏处理按渐进顺序实施，第一阶段不强行隐藏业务字段：

1. 表头最多两行，不允许逐字竖排。
2. 减少非关键单元格内边距，但不压缩触控区域。
3. 长文本最多两行，完整内容可查看。
4. 操作列切换到主操作 + 更多。
5. 保留可横向滚动的表格及明显提示。
6. 在确认页面已有卡片模式且业务功能完整的前提下，优先复用卡片模式；不得为窄屏另造一套丢失排序、筛选、附件或行操作的卡片实现。
7. 低优先级列自动隐藏属于后续可选阶段，必须显示隐藏数量并允许用户恢复。

## 9. 分阶段实施计划

### 阶段 0：建立基线与影响面清单

目标：确认 v2.3.19 正常表现和当前 v2.3.22 真实调用关系。

工作：

- 记录两类记录表在 1024、1280、1440、1920px 下的截图或测量结果。
- 列出 `adaptiveColumns.ts`、`recordTableLayout.ts`、`useTableConfig.ts` 的所有调用者。
- 标出列定义、固定列、选择列、序号列、操作列是否进入同一布局计算。
- 标出当前后台配置到 API、hook、表格 DOM 的完整数据链。
- 不修改业务逻辑，不打包发布。

完成条件：形成页面/列/配置映射清单；确认下阶段修改边界。

### 阶段 1：恢复稳定列宽与最小宽度保护

目标：达到 v2.3.19 的布局稳定性，同时保留 v2.3.22 防塌陷能力。

工作：

- 统一记录表使用同一列宽布局入口。
- 不改变录入表单宽度工具；若有页面仍依赖旧算法，明确其用途。
- 确保选择列、序号列、数据列、附件列、操作列完整纳入表宽计算。
- 保留 callback ref、容器宽度重测和安全回退。
- 保留长表头两行估算及 `title`。
- 保留按可压缩余量压缩和最小宽度保护。
- 放不下时允许横向滚动，不压到最小值以下。
- 暂不改变按钮内容、列隐藏、数据库/API。

完成条件：本方案第 10 节中的首轮宽度验收全部通过。

### 阶段 2：统一操作列呈现

目标：减少操作列对数据列的侵占。

工作：

- RD 与样品信息记录使用统一的操作列布局组件/函数。
- 默认 `auto`，保留 `full` 回退。
- 依据容器档位收纳次要操作。
- 复用当前权限和状态判断，只重新安排呈现位置。

完成条件：不同屏宽下主操作可用、次要动作仍可访问、业务回归通过。

### 阶段 3：打通后台配置

目标：后台配置值确实影响记录表。

工作：

- 统一读取行高、序号宽度、选择框宽度。
- 缺失/失败时回退默认值。
- 将实际宽度应用于对应表头和数据单元格。
- 明确长文本行高下限。
- 验证样品信息表无选择列时不出现空白列。

完成条件：后台逐项修改后，前台刷新/重新计算可观察到相应变化。

### 阶段 4：完善后台和前台列设置 UI

目标：用户可辨识列宽来源并可安全恢复。

工作：

- 后台自动/自定义模式显示方式统一。
- 自动建议宽度与自定义值分开表达。
- 前台列设置显示自动、后台自定义、本机自定义、已隐藏及宽度值。
- 增加单列/整表恢复和溢出提示。
- 保持旧配置兼容。

完成条件：配置来源和恢复行为不含糊，刷新及换用户场景正确。

### 阶段 5：窄屏与移动端整理

目标：窄屏仍可完成主要业务操作。

工作：

- 先复用现有卡片模式，确保字段和操作覆盖。
- 调整触控间距与主操作呈现。
- 若仍需自动隐藏列，再另行定义优先级并提供显示列数提示。

完成条件：窄屏无逐字表头，关键字段和主要操作可访问。

## 10. 验收标准

### 10.1 屏宽测试

至少测试容器宽度：`1024px`、`1280px`、`1440px`、`1920px`。测试应覆盖研发送样记录与样品信息记录，并在表格有无选择列、不同操作档位下重复。

必须满足：

- “序号”“检测类型”等表头不逐字竖排。
- 任一列不低于其有效 `minWidth`。
- 所有参与布局的列宽之和与表格实际宽度一致；选择列不会在计算外额外叠加。
- 容器宽度首次为 0 时，页面仍有可读安全布局，实际宽度到达后正确重算。
- 不足以放下全部列时，横向滚动正常且提示可见。
- 宽屏没有由错误列宽计算造成的大面积空白；有空余时按优先级扩展目标列。
- 1280px 下不要求所有列强塞进视口；最小可读性优先于无滚动。

### 10.2 内容测试

至少包含：

- 批号 `D00260914-11-15`。
- 较长的方法名。
- 较长的主要成分。
- 较长的注意事项。
- 较长的退回原因。
- 长表头 `注意事项（理化检测样品标注大致含量）`。
- 长表头 `检测元素及其精度（铅、镉、砷、汞、铬等）`。

必须满足：

- 长文本最多两行显示并能查看全文。
- 表头完整名称可以查看。
- 单元格内无不可发现的滚动条。
- 行内编辑框、附件按钮和状态徽标不被截断。

### 10.3 配置测试

- 修改行高后，记录表行高随之变化，但两行文本不被裁切。
- 修改序号宽度后，表头与数据列对齐且实际宽度变化。
- 修改选择列宽度后，选择列实际宽度变化；无选择列页面没有空白占位。
- 配置读取失败时使用安全默认值，不崩溃、不出现 0 宽列。
- 后台自定义模式在前台保留对应宽度并标记来源。
- 本机覆盖优先于后台和自动值；恢复本机覆盖后回到后台/自动值。

### 10.4 操作与业务回归

至少覆盖待取样、已取样、待检测、已检测、退回、退回待修改、已作废等实际存在状态，并验证：

- 主操作正确且权限允许。
- 其他操作仍可在“更多”或 `full` 模式中找到。
- 状态和权限规则与改动前一致。
- 服务端排序、本页筛选、列显隐、分页、批量撤回、行内编辑、退回/确认退回、工作量录入、附件查看/上传/下载/删除均正常。
- 移动端卡片或窄屏布局的主要业务能力未丢失。

## 11. 回退策略

1. 每阶段以单独、可审查的代码变更完成，不把全部阶段堆进一次修改。
2. 若阶段 1 布局不稳定，优先回退到 v2.3.19 的比例分配表现，但保留列最小值与完整滚动容器；不得回退到无下限压缩。
3. 若操作列收纳影响操作可发现性，可通过 `full` 模式恢复全量按钮，不能删除或改变业务操作。
4. 后台配置界面异常时，前台仍使用安全默认值；不因 UI 保存失败破坏已有配置。
5. 不清除现有 `localStorage` 列宽数据；如必须调整存储格式，先设计兼容读取和迁移。
6. 打包发布前应记录对应源码提交、前端构建结果、安装包或 Docker 镜像版本，避免源码与发布物不一致。

## 12. 开发执行约束

后续依据本文实施时必须遵守：

1. 先检查当前文件和调用者，再编辑；不得依本文描述猜测代码现状。
2. 每个阶段先列出拟修改文件与行为变化，再实现该阶段，不等待跨阶段的大规模重构。
3. 修改仅限当前 v2.3.22 目标版本，除非明确决定同步其他版本。
4. 不覆盖、清理或删除用户未提交文件和生成资源。
5. 不更改权限、状态流转、API 语义或数据库结构，除非用户另行确认。
6. 每阶段完成后针对修改文件检查诊断，并运行适当的前端构建/测试；构建失败需先修复或明确阻塞原因。
7. 先完成阶段 0 与阶段 1，并由用户检查 UI/安装包效果，再继续阶段 2 以后内容。
8. 需要出包时同时说明完整安装包、热更新包或 Docker 镜像的实际状态；不能把源码构建误称为已推送远端。

## 13. 推荐结论

推荐执行方案 B：

```text
以 v2.3.19 的稳定布局作为体验基线
+ 统一记录表列宽入口
+ 保留 v2.3.22 的长表头和最小宽度保护
+ 操作列主操作/更多收纳
+ 接通后台配置
+ 显示宽度来源并安全支持本机拖拽
+ 最后整理窄屏行为
```

优先原则：

> 可读性高于“所有列必须塞进一屏”；最小宽度高于无条件铺满；业务行为不变高于视觉改造范围。

第一轮只完成阶段 0、阶段 1。确认列宽回到稳定、可读后，再逐阶段推进，避免再次出现列宽算法、操作列、配置界面和移动端同时变化而难以定位问题的情况。
