## 1. 本次目标与边界

本次将权限维护集中到“角色与权限”，减少技术标识和长列表对日常配置的干扰；允许自定义角色选择个人、公共送样或公共检测用途；补齐可维护的角色模板。工作量录入仅整理常显内容和布局，继续沿用送样、选方法、填数量及确认录入的现有习惯。

- 用户管理保留账号资料、归属、角色分配和启停；移除“权限”列及桌面、手机的“实际权限”入口。`is_admin` 等底层账号身份继续保存，不把移除一列理解为删除管理员能力。
- “角色与权限”集中为“角色管理 / 角色模板 / 成员权限查询”三个页签，不增加多层权限引擎、用户直接授权表或额外权限继承层。
- 公共用途由角色维护，不新增“成为公共账号”这样的普通权限 key，也不依据角色名称或账号名称猜测。
- 模板维护默认功能权限；部门、实验室与样品类型范围仍按现有账号、角色及业务规则配置，不在模板重复配置。
- 工作量窗口保持常显紧凑布局，不把来源、日期、倍率或结果改成默认折叠。常规手动录入保留原项目方法行、逐行数量和确认操作。
- 保留旧权限 key、角色 ID、来源模板、历史系数与来源快照、三类范围配对、统计口径和现有自定义配置。

## 3. 页面组织

### 3.1 用户管理

保留用户名、归属、角色、启停和账号维护操作，删除权限明细展示及实际权限按钮。管理员身份保留在已有账号资料或详情中，以“账号类型”解释；不要新增第二套可任意勾选的管理员开关。

账号依旧在用户管理分配角色。角色的公共用途在角色配置维护，账号页面最多显示相应业务说明，不重复提供“个人 / 公共送样 / 公共检测”编辑项。现有“实际送样人必须手填”仍是业务设置，自定义个人账号也可以独立开启，不能随权限入口一起删除。

### 3.2 角色管理

列表展示角色名称、用途、来源模板、成员数与配置摘要；点击“配置”维护功能权限、数据范围和角色用途。

功能权限按业务分组导航，每次只展示当前组。支持中文名称搜索、仅看已选、当前组已选数量和清除搜索。默认不显示技术 key；“显示技术标识”作为排查开关，不能改变提交值。完整规则放在对应项详情或统一“规则说明”中，避免每个复选框重复长段文字。

内部必需项、历史兼容项、服务端未知但已保存的旧项保留在“系统与兼容说明”，不能因为默认不展示就从保存请求中删除。普通权限勾选不自动授予组长身份，不自动补选其他能力；数据范围继续区分研发来源部门、分析来源部门和样品登记类型。

保存沿用现有“一次事务保存功能权限和范围 + 修订校验 + 差异预览”。用途变化也纳入同一次配置提交、审计和受影响会话处理，不拆成两个可能只成功一半的请求。

### 3.3 角色模板

模板列表展示中文名称、说明、默认功能权限摘要、内置 / 自定义、引用角色数，提供“查看、复制、新建、编辑”。模板维护表单只编辑名称、说明及默认功能权限；复制时选择已有模板作为基础，继承稳定业务身份，不给管理员再摆一组可随意组合的身份字段。

模板没有默认部门、实验室和样品类型范围，也不保存公共用途。新角色选择模板后复制功能权限，并在角色配置中选择用途、维护范围。创建模板或复制模板均不会修改成员的当前授权。

默认不提供永久删除。没有引用的自定义模板可停用；有引用的模板可以停止用于新建，但必须继续保留现有角色的身份关联。内置模板及已引用模板的身份不能任意改变，不能由改名、停用或删除操作间接撤销现有组长身份。

### 3.4 成员权限查询

在角色页选择成员，显示服务端计算的能力、授予角色、身份和限制；可筛选已授予、未授予或存在限制的功能。三类范围仍按角色逐组解释，不将不同角色的部门与类型交叉拼成更大的访问范围。

成员选择接口仅返回查询需要的稳定账号 ID、姓名、状态和角色摘要，沿用实际权限查询的查看授权；不调用用户编辑接口，也不扩大原用户列表、导入、导出或账号维护权限。实际权限页面说明的是功能能力，不能承诺所有具体记录都可读写。

## 4. 公共用途与稳定模板身份

最小数据改动为两个用途明确的字段；它们不是两套展示给用户的账号类型。

| 层级 | 建议字段与含义 | 用户配置位置 |
| --- | --- | --- |
| 角色业务用途 | `roles.role_purpose`：个人、公共送样、公共检测 | 角色配置中的一组选项 |
| 模板稳定身份 | `role_templates.identity_key`：沿用分析人员、分析组长、研发送样员、研发组长等受控身份；新模板从基础模板继承 | 程序内部识别；前端只解释身份来源，不开放任意身份字符串编辑 |
| 系统管理员及旧固定公共身份 | 原 `users.is_admin`、`roles.system_key` | 保留原限制，不由新字段、模板权限或 `*` 反推 |

角色用途描述账号使用方式，功能权限仍描述能做什么，数据范围仍描述能接触哪些数据。选择公共检测用途不会自动获得全部部门、他人记录或管理员能力；公共送样也不会自动成为组长。

### 4.1 新旧用途的优先级

| 角色状态 | 用途解释与修改规则 |
| --- | --- |
| 旧固定系统公共角色 | 原 `public_account` / `rd_public_account` 对应公共送样，原 `analysis_public_account` 对应公共检测；用途锁定为原对应值，服务端拒绝冲突值。需要不同用途时复制为自定义角色后配置，不直接改变旧固定角色。 |
| 自定义角色已明确配置新用途 | 使用 `role_purpose`。明确选择“个人”即表示该角色不再提供公共用途，即使保留了历史 `system_key`，也不能用旧 key 的 OR 判断把公共身份补回来。 |
| 新字段尚未配置的历史角色 | 仅此时回退原稳定 `system_key`；无公共 key 则按个人用途。保留“未配置”和明确“个人”的区别，不能用相同默认值抹掉这层兼容语义。 |
| 多角色账号 | 先逐角色按上述优先级解释，再分别合并公共送样、公共检测事实。一个角色改为个人不会撤销另一角色仍明确提供的公共用途；旧双公共多角色仍分别生效。 |
| 旧更新或导入请求不传新字段 | 保留数据库现值，不解释成重置、清空或重新回退旧 key。重复启动也不根据旧 key 覆盖已经明确保存的新用途。 |

旧固定角色和自定义角色的规则不同：固定角色保留原兼容身份；自定义角色一旦明确配置，新字段就是用途权威。判断公共用途的 API、SQL、会话和前端派生结果必须遵守同一优先级，不能在某个入口再次将新用途与旧 key 无条件 OR。

### 4.2 管理身份与公共用途组合

新建角色、主动变更角色用途或分配账号角色时，拒绝“真实系统管理员 / 组长身份 + 公共送样或公共检测用途”的组合。既要检查单个角色的模板身份与用途，也要检查账号多角色合并后的结果；角色用途变更若会让已有成员出现该组合，整次变更拒绝并列出影响范围。前端禁用说明与服务端写入校验同时实现，不能只藏选项。

管理员判断继续使用真实管理员身份，组长判断使用受控稳定身份；`*` 只是权限通配，不因此认定为真实管理员。旧库已经存在的混合组合不自动移除角色、改变用途、清空归属或批量纠正；沿用原授权并显示待复核说明。需要调整其用途或角色组合时，由有权人员预览后明确整理；与用途和授权无关的基础信息编辑不得触发隐式清理。

### 4.3 调用链与模板生命周期

实现时应统一解释有效用途，但不能只修改前端标志：

- 常规录入、辅助录入、样品登记实际送样人规则和工作量归属，均读取服务端解释后的有效用途。公共送样和公共检测两项按各自规则分别判断。
- 旧固定公共角色继续有效；旧账号同时具备两种公共角色时，保留两项事实分别成立，不压成一个丢失信息的枚举。单个新角色的用途仍为单选。
- 检测人候选、辅助工作候选、通知接收者排除及会话时长中的固定 `system_key` SQL 要同步支持新增用途，并继续保留旧 key 兼容。参考 [user_repo.rs:468](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/user_repo.rs:468)、[auxiliary_handler.rs:488](../../source/LabFlow-PostgreSQL-v2.4.13/src/api/auxiliary_handler.rs:488)、[notification_repo.rs:1312](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/notification_repo.rs:1312)、[auth_service.rs:138](../../source/LabFlow-PostgreSQL-v2.4.13/src/service/auth_service.rs:138)。
- `records:work:portal-scoped` 等现有公共检测必需规则按有效用途保留，不能把新增用途做成绕过必需约束的途径。相关现状见 [role_repo.rs:116](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/role_repo.rs:116)。
- 用途变更预览受影响成员、归属缺口和行为变化。缺少必需归属时保留当前配置并明确阻止不完整提交，不自动删掉用户的部门、实验室或角色来让保存通过。

稳定模板身份由新增幂等迁移按旧模板的精确身份一次性回填，不能按包含“组长”等关键词猜测。旧 ID、名称和关联保留。改名只改展示名称；停用仅阻止后续创建使用，已关联角色读取身份时不能用模板 `deleted_at IS NULL` 条件抹掉身份。

复制模板时继承稳定身份；编辑模板权限只影响以后创建的角色。若将来要对既有角色重新应用模板，需另做独立差异预览和显式确认，本轮不增加隐式同步功能。

## 5. 模板接口与保存语义

- 复用现有 `role_templates` 和 `role_template_permissions`，新增管理员专用 POST、PUT 和受控停用接口。旧 GET 保持兼容，可追加权限摘要、引用数及修订等字段。
- 模板创建、修改和停用均在事务中完成校验与审计；更新请求携带 `expected_revision`，并发修改拒绝后保留输入供重新核对。
- 角色创建在事务内读取模板并复核其修订，防止新增编辑功能后复制到不一致的默认权限。创建后角色保存的是自身权限，模板后续修改不回写角色或成员。
- 当前 [role_repo.rs:300](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/role_repo.rs:300) 将空权限数组解释为使用模板默认。保留旧请求含义；若增加“新建时明确清空权限”，用新增显式覆盖字段表达，不能直接重定义旧 `[]` 的语义。
- 旧角色权限 PUT、范围 PUT 继续按原部分更新契约工作；新界面继续使用原子配置接口。服务端未提供必要修订或新能力时，界面只读并解释需要升级，不能退回两个无修订请求冒险覆盖。
- 模板默认权限的编辑不自动使现有成员退出；角色实际权限、范围、用途或身份变化才按影响范围处理会话。不得每次启动根据模板重建角色权限或补回管理员已撤销的授权。

## 6. 工作量录入布局

### 6.1 共用来源录入窗口

| 内容 | 拟采用的常显布局 | 必须保留的行为 |
| --- | --- | --- |
| 来源摘要 | 紧凑 2～3 行：录入人；部门 / 实验室 / 项目；原方法及原始 / 已录 / 剩余数量。长内容自然增加行数 | 完整来源值不截断为不可查看；样品登记原文与实际计量归属明确区分 |
| 实际计量方法 | 主要搜索框；仪器筛选与方法框桌面并排，手机换行；改选后显示简短原方法 → 实际方法提示 | 原方法默认带入；关键词只筛候选，必须确认稳定方法 ID，不自动按名称替换 |
| 计量归属 | 样品登记仍显示部门 / 实验室 / 项目；只有唯一有效授权选项时可展示为紧凑只读值 | 多选、未匹配、已失效或不满足必填时保留选择控件，不能以“精简”为由删除字段 |
| 日期、数量、金额倍率 | 桌面紧凑一组；手机日期整行，数量与倍率并排 | 都可直接编辑；倍率即使默认 1 也不隐藏，手工 0 合法 |
| 计算结果 | 一行只读摘要“工作量 … · 金额 …”，必要时换行；辅以短公式 | 不再以两个只读输入框占行；单价不可用时显示原因，不伪造零金额 |
| 备注与操作 | 备注占整行，可随内容扩展；保存草稿靠左，取消与确认靠右 | 保留现有按钮颜色、业务状态与禁用逻辑；低高度下动作可达 |

仪器只有一个有效选项且没有需要解除的筛选状态时，可用紧凑名称展示；存在多个选项或正在筛选时仍保留可操作控件。清空仪器筛选必须恢复全部授权可用方法，不能产生“库中方法又消失”的新问题。

### 6.2 常规手动录入与辅助工作

常规手录继续沿用现有项目方法行、“更换计量方法”、数量和确认按钮，不改为另一套大表单。实际选中方法与原方法相同时省去重复名称说明；仅改选时提示来源差异。已有工作量 / 金额预览移到行底部常显，不依赖展开方法搜索区。

相关现状见 [EntryPage.tsx:697](../../source/LabFlow-PostgreSQL-v2.4.13/frontend/src/pages/EntryPage.tsx:697)。共享行组件同时被辅助工作使用，调整时优先在调用页面组织内容，不能连带给辅助工作增加金额、实验室或项目分摊。辅助工作继续独立配置区域、事项和系数，人员关联沿用常规录入。

### 6.3 计量与异常规则不变

- 工作量 = 数量 × 方法系数；金额 = 数量 × 当前方法单价 × 金额倍率。明确自定义方法继续按现有项目备用系数处理，倍率不能参与工作量计算。
- 手工倍率包含 0；切换方法保留手改值，只有明确点击恢复才改用方法默认。历史系数与来源快照不自动重算。
- 同一来源采用不同实际方法仍共享剩余数量。保留服务端事务、来源行锁与累计数量复核，见 [record_repo.rs:664](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/record_repo.rs:664)。
- 方法和仪器配置已变化时拒绝过期提交，保留输入并重新核对；原提交方法、实际方法与来源链继续分别保存，见 [record_repo.rs:888](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/record_repo.rs:888)。
- 日期仍是工作量业务时间；服务器校准、历史日期、本人 / 授权代录 / 公共账号归属及录入后记录刷新规则不变。
- 默认说明可以缩短，但校准失败、无候选、授权不足、必填缺失、配置冲突、结果未知等提示必须明确显示。网络结果未知时继续保留输入、暂停直接再次提交，核对记录后再继续，见 [SampleWorkloadDialog.tsx:256](../../source/LabFlow-PostgreSQL-v2.4.13/frontend/src/components/SampleWorkloadDialog.tsx:256)。

## 7. 旧版兼容与数据保护

1. **旧角色读取。** 保留 `users.role_id` 单角色回退及 `user_roles` 多角色契约。有多角色关联时不能把旧主角色额外合并造成扩权；仅有旧 `role_id` 的账号不能因为新用途聚合只查关联表而失去公共或业务身份。当前权限回退见 [user_repo.rs:239](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/user_repo.rs:239)。
2. **旧授权原样保留。** 不重建角色、不替换成员角色、不按模板重置权限、不自动删除未知旧 key。旧固定公共角色用途锁定；自定义角色明确的新用途优先，只有尚未配置才回退旧 key，不用 OR 恢复已撤销的公共身份。旧更新或导入请求未传用途时保留原值，旧双公共多角色分别生效。
3. **范围配对。** 每个角色的部门与类型分别计算，再合并允许的记录集合；不得先合并部门和类型再交叉组合。空范围继续按原业务规则解释，不统一改成全部或无权限。见 [role_repo.rs:159](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/role_repo.rs:159)。
4. **旧接口保留。** 新模板及新配置字段向后兼容；原角色权限 / 范围部分更新 API 不删除。新页面需要的新契约缺失时明确只读，不悄悄套用不等价的旧接口。
5. **会话同步。** 权限、范围和用途实际变更后撤销受影响会话；前端按 `/users/me` 的新身份和授权清理会话草稿。角色改名、模板改名后稳定身份继续有效，不能因名称变化意外获得或丢失组长职责。现有会话撤销见 [role_repo.rs:656](../../source/LabFlow-PostgreSQL-v2.4.13/src/repo/role_repo.rs:656)。
6. **归属与旧混合组合不自动删。** 新建、变更用途或分配角色时，服务端拒绝真实管理员 / 组长与公共用途的新增组合。旧库已有混合组合不自动迁移、删角色或清空部门实验室；保留原事实并提示复核。读取失败、选项暂不可用、字典停用或主动调整发现冲突时，先展示原值和原因，不把归属清空后保存。
7. **迁移幂等。** 新字段和稳定身份回填使用新的迁移标识，不改已发布迁移；重复启动不重新分配角色、恢复权限或猜测人员。
8. **历史业务不动。** 不搬记录、不按姓名合并、不重算历史系数和金额、不改业务日期；公共用途变更只影响后续业务行为及当前有效授权，不改写原录入人与实际人员快照。

## 8. 最小实施顺序

1. 在下一递增业务版本中，以只读快照固定旧角色、权限、三类范围、模板、人员角色关联及公共账号行为基线，准备隔离旧库升级场景。

3. 补齐模板管理员 CRUD、修订保护与事务；保留创建时复制及旧 API 契约。先完成模板改名、停用和复制后的身份验证。
4. 整理角色页三个页签与默认中文权限分组，迁移成员查询入口；随后移除用户列表权限列和按钮，保留用户角色分配与业务设置。
