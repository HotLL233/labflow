# LabFlow v2.3.70：辅助独立配置、固定方法ID与取样通知

辅助事项分别配置名称、区域、辅助类别和独立系数；区域复用液相、气相、理化等已有检测类型，类别只作分类，同类别事项可以使用不同系数。辅助录入与常规手动录入实际复用数量行组件，保留人员、时间、倍率及原业务提交逻辑。

配置调整只影响后续录入；只修改历史记录数量、时间或备注保留原系数、区域和类别快照，主动更换事项才采用新配置。区域是辅助分类维度，工作量仍计入辅助及人员总量，不混入检测、实验室、项目、仪器或金额统计。旧数据保持未分区，不自动推断或重算。

主数据“辅助工作”表增加可选“区域名称”。旧表缺列保留已有区域；有列空值清空，填写名称时校验现有或本次导入的区域。每项独立系数支持0。旧模板缺辅助表保留事项；覆盖导入会软删除遗漏事项，空表软删除全部，必须先核对预检。事项身份仍按名称／范围／所属实验室匹配，区域和类别不扩展同名身份。

版本隔离自正式v2.3.69，源码目录为source/LabFlow-PostgreSQL-v2.3.70。新增可空区域关联及历史区域快照迁移，旧版本不改；共享依赖和运行库仍引用根build-resources，不复制旧构建产物。

主数据导入新增默认“合并更新”：按ID更新或新增表内数据，保留未列实体和项目关联；“覆盖更新”仍以完整Excel为准，遗漏实体会删除并受历史引用保护；“跳过已有”只新增，不改变已有系数。预检显示系数旧值→新值，支持0和小数，缺失或重复系数列阻止导入。此次20→28未生效的根因是覆盖校验失败后改选了跳过已有；本版应选择合并更新。

方法固定ID复用methods.method_code，原非空编号不改，空编号升级时补齐；数据库内部id及历史绑定保持。检测方法、通用方法、项目关联表末尾导出“方法ID”，导入优先按ID匹配，允许更名、换仪器和调系数，项目关联也按ID定位。未知、重复或目标名称／仪器冲突会拒绝；新增行留空自动生成，旧模板缺列仍按原名称／仪器匹配。页面ID只读显示及搜索。

研发送样和样品信息成功取样后，同一事务将该记录对应送样／重新送样站内通知对全部收件人标已读，并刷新当前页面的未读角标。无关记录、退回及人员通知保留。持久化取样确认时间并统一锁顺序，覆盖并发投递、取样后迟到入队和撤回后补投；升级时也清理已取样记录对应的既有未读通知，不删除消息。其他客户端使用已有刷新／轮询机制更新角标。

兼容边界：固定ID保证方法绑定及已存快照不变；旧导出Sheet10的方法名称／类型和部分金额报表的单价仍按当前配置，修改名称、类型或单价可能改变历史报表展示或金额。已存工作量系数仍使用快照，本版不擅自重算历史工作量。

本地验证完成：前端160项测试、类型检查、生产构建及2份gzip逐字节核验通过；Rust格式／编译检查通过，全库先通过288项，4项新增夹具补齐必填关联、序号及唯一业务号后逐项复验通过，累计292项不同测试有效验证，3项原备份恢复专项维持ignore。仅修测试夹具，未因此改业务逻辑。最终默认非console Release通过。独立PostgreSQL上的原记录及通知40项、辅助53项、主数据84项，共177项HTTP检查通过；Excel202项核验通过，原统计总量61.5保持一致。真实Excel覆盖固定ID更名／换仪器、系数20→28与1.04／0、旧模板、合并保留历史、未知及重复ID拒绝。通知覆盖全部收件人、无权限／重复取样不误读、并发与迟到投递。

本地完整包和热更新包已生成并核验产品／文件版本2.3.70.0、大小及SHA-256；本版installer/保留本地构建两包，CI正式包及远端发布结果以根PROJECT_MEMORY.md为准。

未操作生产数据库、现场8000服务或实际安装配置；真实浏览器／手机交互、现场覆盖安装、生产规模压测及容器实际启动尚未验收。

## 开发续接与记忆惯例

- 开始开发或更换设备后，必须先阅读仓库根目录的 `PROJECT_MEMORY.md`。
- `PROJECT_MEMORY.md` 是项目唯一、跨版本、跨设备的长期记忆与开发惯例来源；后续确认的业务规则、技术决策、问题根因、环境约定和发布经验只更新该文件，并随 Git 提交。
- 不再新增或维护按日期记忆、`历史记忆_*.md`、`开发交接_*.md`、`续接提示词_*.md` 或 `HANDOFF.md`；旧版本目录中的同类文件只作历史归档，不得作为当前规则来源或复制到新版本。
- 版本 `更新说明.md` 和专项文档仍按用途维护，但不得复制一套长期记忆。规则冲突时以当前用户要求、当前源码与工作流、`PROJECT_MEMORY.md` 的顺序为准。

1. 本版源码目录：`source/LabFlow-PostgreSQL-v2.3.70/`。行为、验证与交付状态见本版 `更新说明.md` 与根 `PROJECT_MEMORY.md`。
2. Gitee 源码仓库：`https://gitee.com/HotLL233/labflow`（自 v2.3.18 起暂停向 Gitee 推送，仅保留历史仓库）。
3. Docker 部署使用 `docker-compose.deploy.yml`，推荐执行 `scripts/pull-labflow-image.ps1`（Windows）或 `scripts/pull-labflow-image.sh`（Ubuntu）。
4. 脚本按 `LABFLOW_IMAGE_PRIORITY` 依次尝试已配置的镜像地址，成功后再启动 Compose；Gitee 镜像地址未配置时跳过，目前发布仅使用 GHCR。
5. v2.3.19 起 JWT 签名密钥由部署自动生成并保存在数据目录 `jwt_secret`；如需集中管理，可用环境变量 `JWT_SECRET` 覆盖（长度需 ≥16 位）。数据库会话时区跟随程序所在机器，容器部署默认 `TZ=Asia/Shanghai`。
6. 从 v2.3.18 升级到 v2.3.19 后所有已登录会话会失效一次，用户需重新登录，之后重启与升级不再失效。

本包不含任何生产数据库、附件、备份、实际服务器配置、登录凭据或用户本机数据。

本地共享构建资源集中于根 `build-resources/`，其中 `local/target/` 为公共编译缓存，`local/version-cache/` 保留37／38／39等版的独立缓存，`local/static-snapshots/` 保存旧共享入口的静态资源，前端依赖按锁文件隔离。版本目录通过链接引用根资源。使用 PowerShell 7 执行 `./scripts/prepare-local-build.ps1 -WhatIf` 检查；首次缺少依赖时加 `-InstallDependencies` 准备环境。原有安装与发布路径保持兼容，目录说明见 [build-resources/README.md](build-resources/README.md)。

打包口径（v2.3.13 起固化为发布规范）：

- 安装包文件名沿用 `LabFlow-v<版本>.exe`（完整服务器版）与 `LabFlow-v<版本>-HotUpdate.exe`（热更新升级包）。
- 发布流程根据 tag `v<版本>` 自动构建，并**自动提交到仓库根 `installers/` 目录**，同时上传 GitHub Release。
- 本地留档副本放在对应版本目录的 `installer/` 中；该目录被 `.gitignore` 忽略，不进入版本库。
- Docker 镜像由发布工作流推送到 GHCR（`ghcr.io/hotll233/labflow:<版本>` 与 `latest`）；向 Gitee registry 的同步自 v2.3.18 起暂停。
